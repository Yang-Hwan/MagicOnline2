# 관리자 사이트 1차 개발

2026-10-18. 기획: `AdminSitePlan.ko.md`.

## 이번 구현

- 기존 `Server/GameApi`에 Razor Pages 관리자 웹(`/admin`)과 관리자 읽기 API(`/api/admin/*`)를 추가했다. 1차에서는 같은 서버 프로세스/출처로 배포하여 별도 웹과 API 사이의 인증·네트워크 구성을 줄였다. 기획의 독립 `AdminWeb` 프로젝트 분리는 후속 운영 배포에서 진행할 수 있다.
- 회원·경기·재화 조회는 실제 PostgreSQL 자료를 사용한다. 숫자 예시·가짜 매출·가짜 접속자는 표시하지 않는다. 개발 검사 계정도 실제 DB에 포함되어 있으므로 집계에 포함된다고 표시한다.
- 관리자 테이블 3개를 별도 마이그레이션 `002_admin.sql`로 추가했다. 이미 적용된 게임 마이그레이션은 수정하지 않았다.

| 화면 | 연결된 기능 |
| --- | --- |
| 로그인/최초 설정 | 게임과 분리된 관리자, 비밀번호 해시, 실패 잠금, 최초 Owner 생성 |
| 대시보드 | 전체/오늘 가입, 진행 상태 경기, 미정산 분쟁, 영수증 수, DB 조회 시각 |
| 회원 목록/상세 | UUID/로그인 ID/닉네임 검색, 상태 필터, 30건 페이지, 프로필·전적·대전·원장 연결 |
| 차트 | SkillMatch / Attendance / CommonCode 현재 배포본 조회 |
| 대전 목록/상세 | 상태 필터, 양쪽 보고, 규칙/차트 스냅샷, 준비·신호 시각, 영수증, 관련 원장 |
| 재화 | Coin/Jem 필터, 요청 키/회원 검색, UUID 지정 시 잔액·원장 합계 대조 |
| 시스템 | 최고 관리자만 계정/역할 및 생성·로그인 성공/실패·로그아웃 감사 기록 조회 |
| 기본 통계 | 현재 DB의 기본 누적 수치. 활동·매출 집계는 미구현 표시 |
| 결제/운영/고객 지원 | 메뉴와 실제 미연동 상태 안내. 변경/결제 기능을 제공하지 않음 |

개별 경기의 최근 신호는 원본 UTC Unix 밀리초 단위를 명시한다. 일반 날짜는 한국 시간으로 표시한다. 재화는 문자열로 API를 전달해 JavaScript 정밀도 손실을 피한다. 회원 상세에 연결된 최근 경기·원장은 각 최대 30건이며 전체 조회 링크로 이어진다.

## 접속과 실행

기존 게임 서버(5080)와 충돌하지 않게 별도 로컬 5082 포트를 사용한다. 두 프로세스는 같은 DB를 사용하며 게임 자료를 복제하지 않는다. 경기 정산의 행 잠금/영수증을 사용하는 유지보수 작업도 각각 실행되므로 장기 운영은 하나의 GameApi 호스트로 합치거나 작업자를 분리하도록 배포 구조를 확정해야 한다.

```powershell
./Server/GameApi/Start-Admin.ps1
```

접속: `http://127.0.0.1:5082/admin`

1. 개발 PC의 로그인 화면에서 관리자 ID(영문·숫자·밑줄 3~32자)만 입력한다.
2. 관리자가 전혀 없는 최초 접속이면 입력한 ID로 개발용 Owner를 생성하고 로그인한다.
3. 이후에는 같은 관리자 ID로 로그인한다. 이미 관리자가 있으면 다른 ID를 자동 생성하지 않는다.
4. 개발 ID 로그인은 Development 환경의 루프백 접속에서만 가능하다. `Admin:PasswordlessDevelopment=false`로 끌 수 있다.
5. 개발 전용 계정과 세션에는 별도 표식을 저장한다. 운영 환경에서는 이 계정·세션을 거절한다. 기존 비밀번호가 있던 관리자도 개발 로그인 시 그 비밀번호를 변경하지 않는다.

사용자 요청에 따라 비밀번호 설정은 개발 종료 시점으로 미뤘다. 운영 전 개발용 계정의 비밀번호 등록/운영 계정 전환과 MFA를 구현해야 한다. 현재 원래 비밀번호 기반 최초 설정은 개발 ID 로그인을 끈 경우에만 사용할 수 있다.

DB 접속은 기존 GameApi의 .NET user-secrets를 재사용한다. 비밀번호·인증 쿠키·구매 근거를 소스나 문서에 저장하지 않는다. 별도 포트의 관리자 전용 로그인 쿠키는 게임 Bearer 세션과 독립적이다.

## 권한·보호

- Owner / Operator / Viewer 역할을 서버 정책에서 검사한다. 게임 계정 토큰으로 관리자 경로를 승인하지 않는다.
- 30분 절대 만료 쿠키, 매 요청 서버 세션/계정/역할 확인, 로그아웃 시 서버 세션 폐기.
- HttpOnly·SameSite 쿠키, Razor Pages POST 위조 방어, 로그인 IP 요청 제한과 계정별 실패 잠금.
- 로그인·최초 계정 생성·로그아웃과 감사 기록을 같은 DB 트랜잭션에 저장한다. 비밀번호와 토큰은 감사 기록에 넣지 않는다.
- 관리자 페이지에 CSP/프레임 삽입 방지/캐시 금지 등을 적용한다. UI의 DB 값은 Razor 인코딩으로 출력한다.
- 운영 환경의 관리자 경로는 기본 비활성이다. MFA·계정 수명주기·운영 접근 통제를 완성한 뒤 `Admin:Enabled`를 명시해서 활성화해야 한다.

첫 구현은 조회 기능이다. 관리자 계정 추가·역할 변경·비밀번호 복구 UI, MFA, 회원 제재, 자료 내보내기, 차트 배포, 보상/회수, 분쟁 보정은 아직 구현하지 않았다. 현재 감사 기록은 관리자 인증 사건이며 모든 자료 조회 이력을 수집하는 기능은 아니다.

## 빌드와 검증 범위

`dotnet build Server/GameApi/GameApi.csproj -o Logs/AdminWeb --nologo` 완료: 경고 0개, 오류 0개. Razor 화면도 함께 컴파일했다.

ID만 입력하는 개발 로그인 변경도 `Logs/AdminWeb-IdOnly` 출력으로 빌드했다(경고 0개·오류 0개). 관리자 호스트를 새 빌드로 재시작했다. 자동 로그인 시나리오 검사는 실행하지 않았다.

로컬 5082에서 새 프로세스를 실행했고 시작 로그에서 수신 준비를 확인했다. 로그인 페이지와 CSS의 준비 상태 조회는 HTTP 200이었다. 기존 5080 게임 서버는 중지하지 않았다. Codex 오른쪽 브라우저 열기는 대기 상태로 접수됐다.

자동 테스트·브라우저 로그인·실제 관리자 업무 시나리오 검사는 실행하지 않았다. 최초 계정 정보는 사용자에게 입력받는 화면으로 남겼다. 실제 결제, 운영 재화 변경 및 외부 배포는 수행하지 않았다.

## 다음 단계

### 회원 상세 닉네임 수정 추가

회원 상세의 기본 정보 탭에 닉네임과 선택 수정 사유를 입력하는 저장 폼을 추가했다. Owner/Operator만 수정할 수 있으며 Viewer의 직접 POST도 거절한다. 기존 게임 프로필과 동일하게 공백만 있는 값·제어 문자를 거절하고 앞뒤 공백 제거 후 최대 24자를 적용한다.

회원 행을 잠근 뒤 화면에서 읽은 기존 닉네임과 비교하여 동시 변경 덮어쓰기를 막는다. 같은 값의 재요청은 추가 변경/기록을 만들지 않는다. 닉네임 변경과 변경 전후·사유의 감사 기록은 같은 트랜잭션에 저장한다. 감사 필드는 `004_admin_member_edits.sql`로 추가했다. 과거 경기의 닉네임 스냅샷은 수정하지 않는다.

기본 관리자 조회 외에 이 닉네임 변경 업무가 추가된 상태이며, 나머지 제재·보상·차트 편집 등은 아래 후속 범위다. 관리자 화면 저장 동작의 자동 테스트나 실제 회원 닉네임 변경은 수행하지 않았다.

3. 차트 초안·검증·배포·되돌리기, 회원 제재 및 운영 보상/분쟁 처리.
4. Android·iOS 구매와 서버 검증·지급·환불 연동.
