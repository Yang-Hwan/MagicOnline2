# 로컬 DB 전환 작업 결과

2026-10-15. 계획: `LocalDatabaseMigrationPlan.ko.md`. 실행 안내: `../Server/GameApi/README.ko.md`.

## 구현·실행 결과

- `magicCushion` PostgreSQL에 테이블 16개(마이그레이션 이력 포함)를 생성했다. 기존 뒤끝 데이터는 가져오거나 변경하지 않았다.
- C# API를 `http://127.0.0.1:5080`에서 실행했다. DB 연결 문자열은 개발용 .NET user-secrets에 보관했다.
- 가입·로그인·토큰 회전·로그아웃·실패 잠금·프로필·공개 게임 프로필·차트·출석 API를 구현했다. 비밀번호와 토큰의 원문을 DB에 저장하지 않는다.
- 기존 정산 서비스에 PostgreSQL 저장소를 연결했다. 경기 행과 두 지갑 잠금, 전적·원장·영수증·개인 기록을 한 트랜잭션으로 저장한다. 출석도 같은 지갑 잠금을 사용한다.
- 입장료 차감·승자 합계 지급·무승부 반환·기권·생존 신호 기반 연결 만료를 구현했다. 서버 작업자가 양쪽 이탈 및 초대 만료도 처리한다.
- 상세 기록·규칙/이름 스냅샷은 만료 후 정리하고, 영수증·재화 원장·누적 전적은 유지한다.
- Unity의 기존 Backend* 클래스는 씬 참조 호환 이름을 유지하면서 내부를 로컬 API로 교체했다. 로그인 후 차트·출석·프로필을 기다린 후 Photon에 연결한다. Photon 참가자 ID도 새 서버 UUID로 통일했다.
- 결과·기권 요청은 API 주소·사용자별 파일로 보관해 재로그인 이후 재전송한다. 서버 완료 확인 전에는 클라이언트에서 코인을 지급하지 않는다.
- 로비 4구/3구 전적, 결과 화면 정산 상태를 연결했다. 승률은 승/(승+패+무)다.
- 뒤끝 SDK·인증 설정은 Unity Assets 밖에 복구 가능하게 보관했다. 옛 펑션 진단 코드는 비활성 전처리 조건 아래 보존했다. Photon SDK는 유지했다.
- Dockerfile·Railway 설정·시작 스크립트를 작성했다. Railway 가입·배포·과금은 수행하지 않았다.

## 실제 검증

`dotnet run --project Server/GameApi.Tests/GameApi.Tests.csproj -- http://127.0.0.1:5080`

실제 HTTP·PostgreSQL 검사 43개 통과:

- 두 계정 가입·로그인, 대소문자 중복 ID 및 잘못된 인증 거부.
- 토큰 회전·재사용 시 세션 폐기·로그아웃 후 접근 차단.
- 프로필에서 Coin 임의 수정 거부, 공개 프로필에서 Jem·로그인 ID 제외.
- 출석 4회 동시 요청에도 단일 지급.
- 미수락 초대가 상대를 잠그지 않으며, 두 경기 동시 수락 실패 시 입장료 전체 롤백.
- 양쪽 준비 후 입장료 단일 차감, 결과 6회 동시 요청에도 단일 지급.
- 4구 승패·3구 무승부 분리, 기권·한쪽/양쪽 끊김·잔액 부족.
- 함수 예외와 두 번째 사용자 DB 제약 오류 시 전체 롤백.
- 결과 불일치 시 지급 보류, 지갑과 원장 합계 일치.
- 실제 서버 작업자의 상세 기록 삭제·규칙 스냅샷 정리, 삭제 후 영수증으로 재정산 방지.

Unity에서 `Tools > Local Game API > Run HTTP smoke test`를 실행했다. UnityWebRequest·JsonUtility로 가입 → 차트 → 출석 → 프로필 → 로그아웃에 성공했다. `UserSettings/LocalGameApiSmokeTest.json`에 `Ok=true`를 기록했다. 비밀번호·토큰은 출력하지 않았다.

최종 수정 이후 Unity가 생성한 Assembly-CSharp.dll의 갱신 시각을 확인했고 Console 컴파일 오류 0개를 확인했다. 기존 경고와 JSON DTO 필드 초기화 경고는 별도 정리 대상이다.

Arise 씬의 Play를 눌러 Come 로그인 화면 진입과 Console 오류 0개를 확인했다. 증빙: `LocalApiLoginScene.png`. 이 검사는 두 클라이언트가 실제 공을 치고 종료하는 종합 대전 검사와 구별한다.

`pg_dump` 백업을 별도 임시 DB에 복원해 사용자·영수증·마이그레이션 건수를 확인했다. 복원 검증용 임시 DB만 제거하고 백업 파일은 유지했다.

## 남은 검증·출시 작업

1. 개발용 대전 및 일반 공개 Pavilion 경로의 로컬 두 프로세스 검사, 재실행 후 결과 큐 복구, 조기·위조 결과 차단 및 다른 계정 큐 격리는 통과했다. 결과 파일 손상 복구와 Photon·HTTP 동시 전송 장애 주입 후 복구도 통과했다. 두 물리 기기 실전, 실제 마우스·터치 영역/배치, 실제 어댑터·공유기 장애·장기 미전송 및 공개 경기장의 승리·기권 UI는 추가 검증 대상이다. 상세 증빙: `LocalApiClientE2E.ko.md`, `LocalApiResultGuard.ko.md`, `LocalApiRecovery.ko.md`.
2. 서버/클라이언트 규칙 버전 불일치 처리는 구현했다(`LocalApiMatchRules.ko.md`). 새 계약으로 실제 두 플레이어 대전·HTTP/DB 회귀 검사, Photon 인증과 결과 검증 강화, 분쟁 처리 절차는 남아 있다.
3. 기존 뒤끝 실계정·자료 이전: 소유 확인·비밀번호 재설정·ID 매핑이 필요하다. 현재는 새 개발 계정으로 검증했다.
4. 현재 개발용 CSV 시드를 출시용 경기장·출석 보상 코드·초기 재화와 대조.
5. 재시작 자동 로그인용 OS 보안 토큰 저장, 비밀번호 복구·탈퇴 사용자 흐름. 현재 토큰은 메모리에만 둔다.
6. Railway 실제 배포·HTTPS·내부 DB 접속·비용·장애 복구. 운영 DB 실행 권한 분리도 배포 전에 진행한다.

첫 구현 단위인 기반·스키마·인증을 완료했고 기본 API 및 정산·Unity 연결 구현까지 진행했다. 전체 전환 완료 판정은 남은 통합 검증 후에 한다.

## 2026-10-17 사용자 대전 확인 및 서버 회귀 검사

사용자가 직접 빌드한 게임으로 로그인·대전을 진행했고 뒤끝에서 로컬 API로 전환하면서 발생한 오류가 없었다고 보고했다. 사용 기기 수와 개별 정산 수치는 별도로 보고되지 않았으므로 이 확인만으로 두 물리 기기 검사나 잔액·원장 대조까지 완료했다고 판단하지 않는다.

앞선 로그인 실패는 API 서버가 종료된 상태에서 `127.0.0.1:5080` 연결이 거부된 원인이었다. 서버를 다시 실행한 뒤 해당 개발 계정의 로그인·차트·프로필 조회가 성공했다. 로그인 화면은 연결 실패·계정 인증 실패·차트/출석/프로필 로딩 실패를 구분하도록 수정했다.

2026-10-17 실제 로컬 HTTP·PostgreSQL 회귀 검사 47개를 통과했다. 기존 43개 검사에 점수·승자 모순 세 유형의 거부와 거부 후 경기·잔액 보존 검사가 포함됐다. 이번 검사의 개발 계정은 `verify_a_fa54a470906f`, `verify_b_fa54a470906f`이며 비밀번호와 토큰은 기록하지 않았다. 결과 조작 및 다른 계정 큐 격리의 클라이언트 검증 결과는 `LocalApiResultGuard.ko.md`에 기록한다.

최신 개발 빌드 `PracticeMatchTest-20261017-123426`에서 공개 4구·3구의 조기·위조 결과 차단 및 정상 정산, 재실행 후 다른 계정 큐 격리·원래 계정 복구까지 세 검사를 통과했다. 경기당 영수증 1개·개인 기록 2개·입장/정산 원장 4개이며, 검사 계정 7개의 잔액·원장 합계·종목별 전적도 PostgreSQL과 일치했다. 실행 보고서와 DB 근거는 `LocalApiResultGuard.results.json`에 보관했다.

## 2026-10-18 파일 손상 및 동시 통신 장애 복구

재전송 큐에 저장 순서 번호·체크섬·최신 백업을 추가했다. 본문·임시 파일·백업 중 최신 정상본을 복구하고 손상 원본을 보관한다. 모든 사본이 손상된 경우는 별도 확인이 필요하다는 경고를 남긴다. 연결 복구 시 서버 영수증을 먼저 확인해 이미 적용된 연결 만료 정산을 로컬 결과·기권으로 바꾸지 않는다.

빌드 `PracticeMatchTest-20261018-130224`에서 파일 복구 검사 12개와 실제 두 개발 플레이어의 손상 후 재실행·55초 Photon/HTTP 동시 전송 장애·계정 격리 회귀 검사 3개를 통과했다. 세 경기의 영수증·기록·원장과 7계정의 잔액·전적이 일치했으며, 참가자 6명의 본문·백업은 모두 대기 요청 0건·동일 내용·정상 체크섬이었다. 장애 경기는 `BothDisconnected`로 입장료만 반환하고 전적을 기록하지 않았다. 검사 종료 조건도 양쪽 큐의 저장 완료까지 기다리도록 보강했다. 근거: `LocalApiRecovery.ko.md`, `LocalApiRecovery.results.json`.

## 2026-10-15 실제 개발 클라이언트 대전 검증

Windows 개발 플레이어 두 프로세스로 세 시나리오·총 4경기를 실행했다. 4구 0:0 정상 종료 후 입장료 반환 → 재대전 B 기권 → A 31/B 29코인, 3구 B 종료 → 서버 연결 만료 패배 → A 31/B 29코인, 3구 Photon 일시 끊김·복귀 후 정상 무승부 → 양쪽 30코인을 확인했다. 모두 30코인에서 시작했고 경기당 입장료는 1이다. PostgreSQL 영수증·종목별 전적·잔액을 조회했고 6계정 모두 재화 원장 합계와 일치했다.

서버 정산 완료 확인 전 재대전 요청을 막는 조건을 추가했다. 기존 4구 결과 검사의 목표 점수 기대값도 실제 규칙인 3점에 맞춰 수정했으며, 빌드 전 경로·입력·복귀·결과 검사를 통과했다. HTTP·DB 43개 검사도 통과했다. 실행 방법과 제한은 `LocalApiClientE2E.ko.md`를 참조한다.

## 일반 경기장·재실행 복구 검증 및 수정

현재 Consist 스와이프 경기장 카드에서 일반 4구/3구를 각각 실행했다. 기존 가입 폼과 카드 버튼 이벤트 → 대기실 준비 → Pavilion → 시간 종료 → 결과 화면 → 서버 정산 → 재대전 버튼 활성화까지 양쪽에서 통과했다. 입장료 차감 후 표시 캐시 29코인, 무승부 반환 후 결과 라벨 30코인을 확인했다.

일반 대전의 수동 씬 로드와 PUN 자동 씬 로드가 겹쳐 참여자가 두 번 로드되는 문제를 수정했다. UI 애니메이션·풀 효과 지연 작업도 씬 폐기 및 비활성화 시 종료하도록 했다. 서버 프로필을 읽을 때 NetworkManager/PoolPlayer의 코인 표시 캐시를 갱신하고 결과 화면에서 상대 프로필도 다시 읽도록 연결했다.

실제 경기 결과 1건을 파일에 저장한 뒤 전송 전 앱 종료 → 새 프로세스에서 동일 계정 로그인 → 1건 재전송 → 정산 완료 → 메모리/파일 큐 0건을 확인했다. 이번 최종 3경기마다 영수증 1·공통 기록 1·개인 기록 2·입장/정산 원장 4개이며 6계정의 종목별 전적·잔액·원장 합계가 일치했다. `LocalApiPublicAndRestart.results.json`에 증빙을 보관했다. Railway 배포나 기존 뒤끝 실계정 이전은 수행하지 않았다.
