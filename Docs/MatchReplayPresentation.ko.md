# 멀티플레이 리플레이: 상태·연출 이벤트 기록

새로 저장하는 경기는 state-events-2 방식이다. 기존 v1~v3 공 기록과 v4 hud-mesh-1 파일도 읽는다. 바깥 파일은 기존 v4를 유지하고 화면 형식 식별자로 구분한다.

## 경기 중 기록

- 공 위치·회전과 실제 시간축은 최대 30Hz로 기록한다.
- HUD 활성화, 텍스트, 폰트, 색, 위치·크기·투명도, 이미지 ID 등 달라진 상태만 값 복사 형태로 메모리에 남긴다. JSON 직렬화·파일 압축은 경기 종료 후 처리한다. 코드로 생성되는 큐대·HUD 장식·발광·기술 불꽃은 원래 표시 코드에 필요한 수치와 시간만 기록한다.
- 월드 모델은 메시 에셋 ID와 변환값, 스킨 모델은 본 변환값을 기록한다. 파티클은 템플릿 ID·시각·시드와 CPU 시뮬레이션 상태·커스텀 스트림을 기록한다. 재생 시 입자를 다시 방출하지 않고 저장 상태를 적용하므로 하위 입자의 위치도 유지된다. 입자 데이터는 기록한 빌드와 같은 Unity 런타임 버전이 필요하다. 선은 제어점과 너비·색 설정을 기록한다.
- 일반 컴포넌트로 복원할 수 없는 소형 커스텀 Graphic은 변경 알림이 있을 때만 로컬 표시 데이터를 보완 기록한다. 경기 중 전체 화면 정점 투영·베이크·해시·압축을 수행하지 않는다.
- 이미지·모델은 GUID와 서브에셋 ID를 참조한다. 빌드 전 MatchReplayAssetBuilder가 ID 목록과 안전한 파티클 템플릿을 생성한다. 에셋 참조는 파일별로 나누어 필요할 때 로드하며 전체 에셋을 한꺼번에 로드하지 않는다.
- 다운로드한 아바타와 동적 폰트 이미지 등 런타임 에셋은 참조만 보관하고 경기 종료 후 한 번 변환한다. PNG 변환과 파일 압축은 경기 진행 중 수행하지 않는다.
- 최초 등록 후에는 계층 변경 알림으로 새로 생긴 부분만 검색한다. 매 기록 시 장면 전체를 다시 순회하지 않는다. 표시 컴포넌트가 없는 UI 중간 부모도 RectTransform으로 보존하며 Canvas와 Graphic이 함께 붙은 오브젝트도 복원한다.
- Canvas·렌더러의 원래 정렬 순서와 정렬 레이어를 유지한다. 원형 방향 조작부처럼 SpriteRenderer로 표시하는 HUD도 기록한다. 커스텀 UI의 텍스처는 표시별로 적용하며 공유 재질의 텍스처를 덮어쓰지 않는다.
- 프리미엄 큐의 실행 중 생성 메시(본체·움직이는 효과)는 에셋 ID로 조회하지 않는다. 디자인·원본 크기·충전·타격 시각·표시 시각·시점 방향만 기록하고 표시 전용 컴포넌트에서 복원한다. 천둥·성운·불꽃 3종의 원본/재생 메시와 색상 일치 검사를 포함한다.
- Unity가 무시하는 내장 시간 상수의 재질 덮어쓰기 호출은 하지 않는다. 큐·HUD의 코드 연출은 기록된 시각과 상태를 사용한다.
- 마지막 승패·점수·서버 확정 결과, 결과 화면의 표시 변화도 함께 기록한다. 종료 후 최대 8초간 기록하며 저장 창을 열면 그 직전에 확정한다. 저장 창은 포함하지 않는다.

## 재생

재생기는 표시용 컴포넌트만 만든다. 버튼·점수 판정·재화 지급·네트워크 호출·게임플레이 스크립트를 실행하지 않는다. 원래 HUD와 월드 효과를 숨기고 저장된 상태를 복원하며 닫으면 원래 표시를 복구한다.

일시정지·배속은 같은 시간축을 사용한다. 뒤로 이동하면 상태를 초기화하고 지정 시점까지 표시 이벤트만 적용한다. 파티클은 저장한 상태를 직접 복원하며 실제 보상을 재실행하지 않는다.

기록 시 사용한 에셋 ID가 있는 빌드가 필요하다. 이후 에셋이 삭제·교체되면 이전 리플레이 호환성도 검증해야 한다. 음향은 이 화면 리플레이 형식의 기록 대상이 아니다.

## 검증·성능 측정

- Logs/replay-state-validation.request에 validate를 쓰면 에셋 ID 생성과 상태 기록·파일 왕복·승패·되감기·표시 복원 검증을 실행한다. build는 Build/Windows/MagicOnline2.exe 개발 빌드까지 만든다.
- 결과: Logs/replay-state-validation.json.
- 클라이언트의 -replay-performance 옵션 뒤에 JSON 경로를 지정하면 경기 중 프레임 시간과 기록 작업 시간을 측정한다. -replay-recording-off를 추가한 동일 경기와 비교한다.
- Server/GameApi/Run-ClientE2E.ps1 -Mode public은 두 로컬 클라이언트의 일반 대기실→Pavilion→결과 경로, 저장 파일 작성·재생 구간 이동을 검사한다. -ReplayBaseline은 기록하지 않는 비교 실행이다. 실행 폴더의 성능 JSON, 리플레이 검증 JSON, 원본/재생 결과 PNG를 확인한다.
- 숨김 테스트 창은 화면 출력이 검게 캡처될 수 있으므로 결과 이미지 검증은 실제 카메라와 UI를 별도 렌더 타깃에 렌더링한다. 결과 화면 이미지의 평균 RGB 차이를 검사하며, 파티클 위치·색·크기와 UI 부모 앵커는 별도 검증한다. 한 PC의 두 클라이언트 측정이며 두 실제 PC 사이의 네트워크 품질이나 모든 연출 조합을 검증한 것은 아니다.
- 120,000프레임, 표시 영역 256MiB 상한을 유지한다. 기록 오류는 시합 진행을 중단하지 않으며 불완전한 리플레이를 정상 저장하지 않는다.

## 2026-11-21 실측

- Windows 개발 빌드, 같은 PC의 숨김 클라이언트 두 개, 각각 960×540 조건이다. 화면 비교는 별도 렌더 타깃에서 수행했다. 전체 화면 GPU 성능이나 두 실제 PC 간 지연을 뜻하는 수치가 아니다.
- 일반 대기실→Pavilion→결과→저장→재생·되감기: 양쪽 통과. 원본/재생 결과 화면 평균 RGB 차이 A 0.078%, B 0.072%로 1% 기준을 통과했다. 검증 폴더: Logs/LocalApiE2E/public-4397babedf2a41f28dbc68f6bc32618f.
- 해당 실행의 기록 작업은 평균 약 3ms였다. 약 79초 경기의 저장 파일은 약 1.10MB였다. 최초 에셋·계층 등록의 단발 비용은 별도이며 테스트 과정에서 약 0.3~0.8초의 진입 지연이 관찰됐다.
- TableSet07 실제 물리 샷과 정상 종료 경기의 저장·재생·무승부 결과 보존도 양쪽에서 확인했다. 풀링 시 Coin_LightUp이 CoinLightUp으로 바뀌는 경우도 같은 템플릿을 연결한다.
- 재대결 테스트의 두 번째 라운드는 방 이탈에 의한 항복 정산 경로다. 결과 화면에 도달한 정상 완료 경기에서만 리플레이 저장을 검사하며, 방 이탈 경기를 정상 완료 저장으로 취급하지 않는다.
- 최종 Windows 빌드는 19개 상태·파일·표시 회귀 검사를 통과했다. 런타임 소스 471개를 플레이어 PDB의 SHA-256과 대조해 모두 일치했다. 최종 실제 샷·정상 경기 저장·재생·재대결·항복 정산은 Logs/LocalApiE2E/rematch-fdea0165c0594110b3b6404f5a659ea6에서 양쪽 PASS를 확인했다. 경기 기록 평균 비용은 약 3~3.4ms였다.
