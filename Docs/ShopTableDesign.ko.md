# 상점 테이블 설계 제안

작성일: 2026-11-10  
상태: 구현 전 설계 제안. 테이블명과 필드명은 논리 설계 기준이며 실제 스키마는 구현 단계에서 확정한다.

## 1\. 요구사항

* 구매 대상은 보석, 큐대, 캐릭터, 메시지 묶음의 네 종류다.
* 보석은 현금으로 구매하고 큐대·캐릭터·메시지 묶음은 보석으로 구매한다.
* 큐대는 디자인, 파워, 팔로스루, 당점, 대기시간 등으로 차이를 둔다.
* 캐릭터는 기본, 감사, 미안, 미소, 환희, 짜증, 우울, 좌절, 분노 등의 감정별 이미지를 가진다.
* 메시지는 기본형, 까칠, 소심, 짜증 등의 성격별 묶음으로 구성한다. 각 묶음에는 약 5개의 채팅 메시지가 들어간다.
* 앱 배포 후에도 상품과 이미지를 외부에서 추가·관리할 수 있어야 한다.

## 2\. 설계 방향과 기본 제안

상품 공통 정보, 상품 종류별 상세 정보, 사용자 보유 정보, 이미지 파일 정보를 분리한다. 캐릭터의 감정과 메시지 문장은 각각 행으로 저장해 항목 추가 시 테이블 구조를 바꾸지 않도록 한다.

2026-11-12 답변을 반영한 구매·사용 기준은 다음과 같다.

* 큐대·캐릭터·메시지 묶음은 영구 소유한다.
* 보석 상품만 반복 구매할 수 있다. 추후 도입할 전체 큐대 기간 이용권은 영구 소유와 별도로 관리한다.
* 멀티플레이에서는 보유한 메시지 묶음을 여러 개 선택할 수 있다. 큐대와 캐릭터는 각각 하나를 장착하는 안이다.
* 메시지는 성격별 묶음 단위로 구매한다.
* 보석 잔액은 기존 재화 잔액·원장 구조를 사용한다.

## 3\. 공통 상품

### ShopProduct

|필드|용도|
|-|-|
|ProductId|변경하지 않는 상품 고유 ID|
|ProductType|GemPack / Cue / Character / MessagePack|
|Name|상품명|
|Description|상품 설명|
|ThumbnailAssetId|대표 이미지 참조|
|PriceGem|보석 가격. 현금 상품은 비워둠|
|SortOrder|표시 순서|
|SaleStartsAt, SaleEndsAt|판매 기간. 상시 판매는 비워둠|
|IsVisible|상점 표시 여부|
|IsPurchasable|구매 가능 여부|
|UpdatedAt|수정 시각|

판매 중지와 기존 보유자의 사용 가능 여부는 구분한다. 판매를 중단한 상품도 기존 구매자는 계속 사용할 수 있어야 한다. 판매 이력이 있는 상품은 삭제보다 비공개·판매 중지로 관리하는 것이 좋다.

## 4\. 보석 상품과 현금 결제

### GemPack

|필드|용도|
|-|-|
|ProductId|공통 상품 연결|
|GemAmount|기본 지급 보석|
|BonusGemAmount|추가 지급 보석|

### StoreProductMapping

|필드|용도|
|-|-|
|ProductId|보석 상품 연결|
|Store|결제 스토어 구분|
|StoreProductId|해당 스토어에 등록한 상품 ID|

현금 가격을 PriceGem과 혼용하지 않는다. 보석 상품을 결제 스토어의 상품과 연결하고 가격 표시는 해당 결제 환경과 연동한다.

보석 지급은 서버에서 결제를 검증한 뒤 한 번만 처리한다. 클라이언트의 구매 성공 메시지만으로 지급하지 않는다. 같은 결제 거래의 재요청이 중복 지급으로 이어지지 않도록 거래 식별자의 고유성을 보장해야 한다.

## 5\. 큐대

### CueDefinition

|필드|용도|
|-|-|
|ProductId|상품 연결|
|VisualAssetId|큐대 이미지 또는 프리팹 리소스|
|PowerPct|기본 파워 대비 -40% ~ +20%|
|FollowThroughPct|기본 팔로스루 대비 -40% ~ +20%|
|TipRadiusPct|중앙에서 선택 가능한 최대 당점 반경 대비 -10% ~ +10%|
|ShotTimeDeltaSeconds|경기장의 샷 준비시간 대비 -5초 ~ +5초. 초 단위 저장 제안|
|BalanceVersion|성능 설정 버전|

현재 정해진 성능은 명시적인 컬럼으로 관리하는 것을 권한다. 임의의 JSON에 모든 능력치를 넣는 방식보다 입력 검증과 밸런스 관리가 쉽다.

퍼센트 필드의 0은 기본값이며 적용값은 기본값 × (1 + 보정률 / 100)이다. 예를 들어 기본 최대 당점 반경이 80이라면 +10% 적용 시 88이다. 실제 물리에서 허용하는 최대 반경 안에서 UI와 샷 계산에 같은 값을 쓴다. 샷 준비시간은 기본 30초인 경기장에서 25~35초가 된다. 퍼센트로 통일할 수도 있지만 경기장별 기본 시간이 다르면 같은 비율의 초 단위 효과도 달라진다.

진행 중인 경기에서 관리자 설정 변경으로 성능이 달라지지 않도록 경기 시작 시 큐대 성능을 경기 규칙에 기록하는 방식을 권한다.

## 6\. 캐릭터와 감정별 이미지

|-|-|
|ProductId|상품 연결|
|DefaultEmotionCode|기본 감정|

### CharacterEmotion

|필드|용도|
|-|-|
|CharacterProductId|캐릭터 연결|
|EmotionCode|기본 / 감사 / 미안 / 미소 / 환희 / 짜증 / 우울 / 좌절 / 분노 등|

CharacterProductId와 EmotionCode의 조합은 중복되지 않게 한다. 감정마다 컬럼을 추가하는 대신 감정 하나를 행 하나로 저장한다. 특정 감정 이미지가 없으면 기본 이미지로 표시한다.

### MessagePackDefinition

### MessagePackItem

|필드|용도|
|-|-|
|MessageId|문장 고유 ID|

구매 단위는 성격별 메시지 묶음으로 제안한다. 약 5개라는 개수는 관리자 화면의 운영 기준으로 두고 DB 구조에서는 고정하지 않는다. 추후 문장 수가 늘어나도 구조를 유지할 수 있다.

## 8\. 사용자 보유·장착·구매 기록

|테이블|역할|
|-|-|
|UserInventory|사용자가 보유한 큐대·캐릭터·메시지 묶음|
|UserEquipment|현재 장착한 큐대·캐릭터|
|UserSelectedMessagePack|멀티플레이에서 선택한 보유 묶음마다 한 행. 회원과 묶음 조합은 고유|
|UserCuePass (추후)|전체 큐대 사용권의 시작·만료 시각. 기간 만료 후에는 영구 보유 큐대만 선택 가능|
|ShopPurchase|구매 상품, 실제 지불 보석, 구매 시각 등의 이력|
|PaymentTransaction|현금 결제 검증 상태와 보석 지급 처리 기록|

보석은 인벤토리 아이템으로 중복 관리하지 않고 기존 보석 잔액·원장 구조에 연결한다. 실제 구현 시 기존 서버의 테이블·서비스와 대조해 중복 구조를 피한다.

보석으로 상품을 구매할 때 다음 작업을 서버의 하나의 DB 트랜잭션에서 처리한다.

1. 판매 상태, 서버 가격, 보유 여부를 확인한다.
2. 보석을 차감한다.
3. 상품 보유 정보를 추가한다.
4. 구매 이력과 재화 원장을 기록한다.

재전송 시 중복 차감을 막기 위해 구매 요청 ID를 사용한다. 영구 소유 상품은 사용자와 상품 조합에 중복 보유 제한을 둔다. 클라이언트가 보낸 가격을 결제 기준으로 사용하지 않으며, 장착 요청도 서버에서 보유 여부와 상품 종류를 확인한다.

## 9\. 외부 이미지와 리소스 관리

상품 데이터는 DB와 관리자 사이트에서 관리하고 실제 이미지 파일은 외부 파일 저장소와 CDN에서 제공하는 구성을 권한다.

### ContentAsset

|필드|용도|
|-|-|
|AssetId|리소스 고유 ID|
|Url 또는 StorageKey|파일 위치|
|ContentHash|파일 변경 확인|
|ContentType|PNG, WebP, AssetBundle 등|
|Width, Height|이미지 크기|
|Version|리소스 버전|

Unity는 서버에서 상품 목록과 리소스 정보를 받아 필요한 파일을 다운로드하고 로컬에 캐시한다. 파일 교체 시 같은 URL의 내용을 덮어쓰기보다 버전별 파일을 사용해 캐시를 관리한다.

|리소스 종류|제안 방식|
|-|-|
|상품 썸네일, 캐릭터 감정 등 단순 이미지|외부 이미지 다운로드와 로컬 캐시|
|큐대 프리팹, 재질, 애니메이션 등 Unity 리소스|원격 Addressables 등 리소스 배포 구조 검토|

이미 앱이 지원하는 동작 범위 안에서는 상품 데이터와 리소스 추가로 새 상품을 제공할 수 있다. 새로운 능력치 계산이나 감정 동작 등 앱 코드가 필요한 기능은 앱 업데이트가 필요하다.

## 10\. 관리자 운영 흐름

1. 리소스를 업로드하고 상품을 임시 저장한다.
2. 가격, 성능 범위, 감정 이미지, 메시지 문장 등 필수 정보를 검증한다.
3. 미리보기에서 상품 표시와 리소스를 확인한다.
4. 상품을 게시해 상점에 공개한다.
5. 수정·판매 중지 이력을 남긴다.

임시 저장과 게시를 구분하고 필요한 파일이 준비되기 전에 상품이 공개되지 않게 한다. 기존 구매자와 구매 기록이 참조하는 상품 ID 및 리소스를 보존해야 한다.

## 11\. 확정한 운영 규칙과 남은 선택

|항목|확정 내용|
|-|-|
|소유와 구매|큐대·캐릭터·메시지 묶음은 영구 소유하며 같은 상품은 한 번만 구매한다. 보석 팩은 반복 구매할 수 있다. 일정 기간 모든 큐대를 사용하는 쿠폰은 추후 상품으로 계획한다.|
|큐대 성능|파워와 팔로스루는 각각 -40% ~ +20%, 당점 반경은 -10% ~ +10%, 샷 준비시간은 -5초 ~ +5초다. 시간 저장 단위는 5절의 제안대로 초 또는 기준시간을 정한 퍼센트 중 선택한다.|
|기본 지급|회원가입 시 무료 큐대·캐릭터·메시지 묶음을 지급한다. 지급할 상품 ID와 기존 회원의 최초 지급 방법은 출시 전에 정한다.|
|메시지 선택|구매하거나 기본 지급받은 여러 묶음을 동시에 선택해 멀티플레이에서 사용한다.|
|캐릭터|기본·감사·미안·미소·환희·짜증·우울·좌절·분노의 9종이 필수다. 현재 멀티플레이의 BandanaAvatar와 SilverAvatar 기본 이미지와 같은 384 × 416 투명 PNG를 기준으로 한다. 현재 경기의 득점·실패·파울과 새 감정의 대응은 별도로 정한다.|
|수정 적용|로그인할 때 게시된 차트를 한 번 받는다. 접속 중 관리자 수정은 다음 로그인부터 기존 보유자의 성능·문장·이미지에도 적용한다. 구매 이력에는 결제 당시 값을 보존한다.|

**이미지 배포 제안.** 기본 아바타와 기본 큐대는 앱에 포함한다. 새 상점 썸네일·감정 PNG는 웹 서버에 올리고 차트에 파일 주소와 버전을 등록하면 다음 로그인부터 앱 업데이트 없이 교체할 수 있다. Unity는 필요한 파일만 받아 캐시한다. 다운로드 실패 시 같은 캐릭터의 기본 표정, 그것도 없으면 앱에 포함한 기본 아바타를 표시한다. 기존 서버를 쓰면 별도 배포 서비스 가입 없이 시작할 수 있으며 실제 비용은 저장 공간과 전송량에 따라 달라진다.

Addressables는 이름으로 Unity 리소스를 불러오는 기능이다. 신규 큐대의 모델·재질·애니메이션을 앱 밖에서 추가하려면 이 파일들을 플랫폼별로 묶어 빌드해 서버에 게시하는 방식이 적합하다. 초기에는 내장 큐대와 외부 PNG로 시작하고 새 프리팹의 독립 배포가 필요해질 때 도입하는 안이다. [Unity 원격 콘텐츠 배포](https://docs.unity3d.com/Packages/com.unity.addressables@1.21/manual/remote-content-distribution.html)

**현금 결제 제안.** 보석 팩 구매 시 앱은 스토어 결제창을 열고, GameApi는 결제 증빙의 진위와 상품·회원 연결을 확인한다. 대기 또는 지급 전 취소는 지급 0건으로 처리한다. 구매 완료가 확인되면 거래 기록·보석 원장·잔액을 한 트랜잭션으로 저장한다. 같은 거래를 재전송하면 기존 결과를 반환하고 새로 결제한 거래는 다시 지급한다. 지급 후 환불이 확정되면 원거래와 연결한 회수 내역을 한 번만 기록한다. 출시 스토어와 이미 쓴 보석의 부족분 처리 방식은 미정이다. [Google Play 구매 검증](https://developer.android.com/google/play/billing/security) · [Apple 환불 알림](https://developer.apple.com/documentation/storekit/handling-refund-notifications)

**서로 다른 시점에 로그인한 두 선수.** 경기 시작 시 서버가 각 선수의 로그인 차트 버전과 장착 큐대로 계산한 실제 샷 성능을 두 클라이언트에 동일하게 전달하는 방식을 제안한다. 관리자 수정 전후에 로그인한 선수가 만나도 같은 샷의 물리 계산이 일치한다.

이 문서는 설계 의견을 정리한 것이며 DB 마이그레이션, 관리자 기능, Unity 상점 및 결제 구현은 포함하지 않는다.
