# 뒤끝 → 로컬 API·PostgreSQL 전환 계획

작성일: 2026-10-15. 이 문서는 계획이며 전환 구현 완료를 의미하지 않는다. 실제 구현·검증 상태는 `LocalDatabaseMigrationProgress.ko.md`를 따른다.

## 목표와 현재 상태

뒤끝 회원 인증, 게임정보, 차트, 출석, 경기 기록 및 펑션 의존성을 자체 C# API와 PostgreSQL로 전환한다. 로컬 검증 후 같은 API·스키마를 Railway에 배포한다. Unity가 PostgreSQL에 직접 접속하지 않는다.

- 로컬 PostgreSQL 18 서비스가 실행 중이며 DB `magicCushion`과 동명의 전용 계정으로 접속을 검증했다. 생성 직후 public 사용자 테이블은 0개다.
- DB 비밀번호는 소스·Unity·문서에 저장하지 않고 서버 개발 비밀 설정으로 전달한다.
- Photon PUN의 실시간 대전·방 통신은 이번 전환에서 유지한다. 뒤끝 제거가 Photon 제거를 뜻하지 않는다.
- 기존 소스에는 수정·미추적 파일이 많이 있다. 시작 전 기준 상태를 기록하고 기존 작업을 덮어쓰지 않는다.
- 뒤끝 지원 답변: https://community.thebackend.io/t/sdk/12074/3. Where는 커밋 시 조건을 재검사하지 않으므로 기존 동시 요청 테스트를 정산 안전성의 증거로 사용하지 않는다.

## 1. 기반 구성 및 교체 범위 고정

`Server/GameApi`에 ASP.NET Core API, `Server/GameApi.Tests`에 API·DB 통합 검증을 구성한다. DB 접속은 Npgsql 기반으로 하고 버전 관리되는 마이그레이션을 둔다. 기존 정산 프로젝트 참조를 연결하되 Unity 데이터 클래스에 대한 서버 결합은 DTO/도메인 모델로 단계적으로 분리한다. 개발 시 localhost에 바인딩하고 API 주소는 Unity 환경 설정으로 분리한다.

완료 기준: 상태 확인 API와 실제 DB 쿼리가 성공하고, 개발 비밀 설정·실행/중지·마이그레이션 방법이 문서화된다. 아직 게임 저장 경로는 변경하지 않는다.

## 2. DB 스키마·초기 데이터 구성

| 테이블(계획 이름) | 책임 |
| --- | --- |
| Users / UserProfiles | UUID 사용자 ID, 정규화한 로그인 ID의 유일성, 비밀번호 해시, 계정 상태, 닉네임·레벨·아바타 |
| RefreshTokens | 갱신 토큰 해시, 만료·폐기·회전 이력, 사용자 연결 |
| Wallets / WalletLedger | Coin·Jem 잔액과 재화 변동 원장. 초기 지급·출석·정산도 동일 경로 사용 |
| UserStats | 사용자별 Ball_4_Win/Lose/Draw, Ball_3_Win/Lose/Draw. Win/Lose는 과거 미분류 자료 보존 목적 |
| CommonCode / SkillMatch / AttendanceRules | 공통 설정, 경기장·규칙·입장료, 출석 보상 기준 |
| UserAttendance / UserAttendanceTerm | 사용자별 출석·기간 진행 상태·보상 중복 방지 |
| Matches / MatchPlayers | 서버 발급 경기 ID, 참가자, 준비·시작·진행 상태, 규칙 스냅샷, 결과 보고·최근 생존 시각 |
| SettlementReceipts | 경기별 유일한 최종 정산 영수증. 상세 기록 삭제 후에도 중복 지급 방지에 사용 |
| MatchHistory / UserMatchHistory | 경기 및 개인별 조회용 상세 기록. 약 6개월 보관 |

Coin은 정수 BIGINT, 잔액 음수 금지, 시간은 UTC, 사용자·경기 외래키와 경기 ID 유일성을 적용한다. API는 재화·전적의 임의 필드 수정을 받지 않는다. 승률의 무승부 포함 여부를 명시하고 화면과 서버에서 동일하게 사용한다.

`Docs/BackendSeed/CommonCode.csv`, `SkillMatch.csv`, `Attendance.csv`를 초기 자료로 사용하되 현재 운영 설정과 일치한다고 가정하지 않는다. 열·값·중복·활성 여부를 검증하고, 차이가 있으면 최신 내보내기와 대조한다. PrizeCoin의 기존 의미를 유지하면서 서버 내부에서는 입장료로 명확히 매핑한다.

완료 기준: 빈 DB에 마이그레이션·시드를 재현할 수 있고 FK·유일성·재화 제약이 검증된다.

## 3. 회원 인증·계정 세션 구현

회원가입, 로그인, 토큰 갱신, 로그아웃, 내 계정 조회를 구현한다. 프레임워크의 검증된 비밀번호 해시를 사용하고 사용자 ID는 서버가 발급한다. 로그인 시도 제한, 계정 차단, 만료 토큰·폐기 토큰 거부를 처리한다. 갱신 토큰은 DB에 해시로 저장하고 Unity의 비밀번호·토큰 로그를 금지한다. 장기 토큰의 기기 저장은 대상 OS의 보안 저장 방식을 적용한다.

기존 UI의 게스트 경로는 제거하거나 서버가 발급하는 복구 가능한 게스트 세션으로 교체한다. 뒤끝 GuestLogin을 남기지 않는다. 비밀번호 찾기·복구는 로컬 검증 중 개발 계정 초기화로 제한하고 출시 전 실제 복구 수단을 별도 완성한다.

완료 기준: 별도 두 계정 가입·로그인·갱신·로그아웃 및 다른 사용자의 비공개 정보 접근 거부를 실제 API로 검증한다.

## 4. 기본 데이터·출석·재화 API 구현

프로필·닉네임·아바타, 경기장·공통 설정, 출석 조회·보상 수령 API를 구현한다. 닉네임 등 허용된 필드만 수정하고 Coin·Jem·전적은 서버 업무 API만 갱신한다. 가입 초기 보상은 중복 생성되지 않게 처리한다. 출석 기준일은 한국 시간으로 계산하고 UTC 시각과 구분해 저장한다.

완료 기준: 로그인 후 프로필·경기장 목록이 표시되고, 출석 보상 재요청에도 한 번만 지급된다. 기존 재화 쓰기 경로 전수 조사로 출석·정산 사이 덮어쓰기 가능성을 제거한다.

## 5. 경기 등록·시작·정산 저장소 구현

서버가 경기 ID·규칙·입장료를 정하고 두 참가자의 인증과 동의를 확인한다. 양쪽 준비가 완료되면 입장료를 한 번만 차감한 뒤 경기 시작 상태를 확정한다. API 실패 시 경기를 시작한 것으로 처리하지 않는다.

기존 SettlementService에 PostgreSQL ISettlementStore를 구현한다. 경기 행과 두 사용자 지갑·전적 행을 일정 순서로 잠그고, 영수증·원장·개인 기록까지 같은 트랜잭션에 반영한다. 서로 다른 경기와 출석 등에서 같은 지갑을 수정하는 경우도 동일한 잠금 규칙을 적용한다. DB 유일성 제약과 제한된 충돌 재시도로 중복/경합을 처리한다.

승자에게 입장료 합계 지급, 무승부·취소 시 규칙에 따른 반환, 4구·3구 전적 분리 규칙을 적용한다. 클라이언트가 승자·점수·잔액을 보냈다는 이유만으로 지급하지 않는다. 정상 종료는 양쪽 보고 일치와 규칙 검사를 적용하고, 불일치는 분쟁 상태로 둔다. Photon 클라이언트 보고 기반 검증의 한계와 권위 게임 서버까지의 범위 차이를 문서화한다.

완료 기준: 실제 PostgreSQL에서 동일 경기 동시 종료, 서로 다른 경기의 동일 사용자 경합, 잔액 부족, 트랜잭션 중 오류, 응답 유실 뒤 재요청을 검증한다. 잔액·원장·전적·영수증이 항상 일치해야 한다.

## 6. Unity 인증·데이터 경로 전환

공통 ApiClient, 인증 세션, 프로필·차트·출석·경기 서비스 인터페이스를 도입하고 화면에서 뒤끝 SDK 응답 타입을 제거한다. 씬·프리팹 참조를 유지하며 단계별로 교체한다.

Arise → Come 로그인/가입 → 로비·경기장 목록 → 대전·결과 화면 순서로 검증한다. Photon의 uuid와 재대전·상대 조회에는 새 서버 사용자 ID를 일관되게 사용한다. 외부에 노출된 Photon 사용자 ID만으로 경기 API 권한을 부여하지 않고, 타 계정 ID 위조를 검사한다.

로컬/배포 주소만 환경별 변경하고 DB 연결 문자열은 Unity에 포함하지 않는다. 단말 테스트에서 localhost는 해당 단말 자체를 뜻하므로 개발 PC LAN 주소·방화벽·개발용 HTTPS 연결을 별도 구성한다.

완료 기준: 뒤끝 로그인 없이 두 계정이 로그인해 같은 경기장에 입장하고 결과·잔액·전적을 서버에서 다시 불러온다. 서버 중단 시 명확한 오류를 표시하고 뒤끝으로 자동 우회하지 않는다.

## 7. 연결 끊김·재전송·기록 보관

진행 중 인증된 생존 신호를 서버 시각으로 기록하고 재접속 대기를 처리한다. 남은 클라이언트는 판정을 요청할 수 있지만 상대 코인을 직접 수정하지 않는다. 기존 대기 규칙과 양쪽 이탈 취소·반환 규칙은 서비스 코드와 대조해 확정한다. 양쪽 모두 앱을 종료해도 서버 작업자가 만료 경기를 처리하도록 한다.

미완료 결과는 사용자 ID·서버 환경별로 분리해 보관하고 로그인 이후 같은 경기 ID로 재조회·재전송한다. 이전 뒤끝용 큐를 새 계정의 정산 입력으로 사용하지 않는다. 결과 화면은 대기·완료·분쟁·오류를 구분한다.

상세 기록은 약 6개월 뒤 배치 삭제하되 진행·분쟁 중 경기는 제외한다. 영수증·필수 원장·누적 전적은 상세 기록과 별도 보존하며 기록 삭제가 재정산을 유발하지 않아야 한다.

완료 기준: 한쪽/양쪽 이탈, 재접속, 계정 전환, 서버 재시작, 응답 유실 및 상세 기록 삭제 후 재요청을 검증한다.

## 8. 데이터 이전·뒤끝 의존성 제거·배포 준비

로컬 개발은 신규 테스트 계정으로 시작한다. 기존 회원 비밀번호를 가져올 수 있다고 가정하지 않는다. 기존 자료 이전 시 LegacyUserMap으로 뒤끝 ID와 새 UUID를 연결하고 계정 소유 확인/비밀번호 재설정 절차를 별도 적용한다. 코인·기록 이전은 원본 스냅샷과 합계·건수 대조, 재실행 중복 방지, 변경 동결 및 복구 계획이 필요하다. 기존 자료를 폐기할지 실제 이전할지는 사용자 결정 전까지 보존한다.

실행 코드·Editor 도구·씬·프리팹에서 BackEnd, Backend.UserInDate, 펑션 호출, CDN 차트 의존성을 조사한다. LitJson 등 SDK와 함께 제공되던 의존 라이브러리도 확인한 후 SDK를 제거한다. Photon은 유지한다.

Dockerfile, Railway용 포트·환경 설정·상태 검사·마이그레이션 절차를 로컬에서 준비한다. 로컬 통합 검증 완료 후 Railway에 가입·배포하고 TLS, 내부 DB 연결, 두 단말 접속, 백업·복원, 비용 설정을 실제 환경에서 확인한다. 이 단계 전에는 Railway 가입이 필요하지 않다.

완료 기준: Unity 컴파일/실행과 서버 DB 통합 검증이 통과하고 뒤끝 서비스 연결 없이 시작→로그인→대전→정산→재로그인 조회가 동작한다. 실제 Railway 동작·요금은 배포 전까지 확인 완료로 표시하지 않는다.

## 첫 구현 단위

1~3단계를 묶어 로컬 API 실행, 스키마 생성, 개발용 두 계정의 로그인까지 먼저 완성한다. 이후 4단계와 Unity 로그인·로비 전환을 연결한 다음 경기 정산으로 확장한다. 이번 계획 작성에서는 테이블·운영 데이터·기존 게임 소스를 변경하지 않는다.
