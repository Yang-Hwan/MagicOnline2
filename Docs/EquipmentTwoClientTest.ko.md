# 장비 적용 두 클라이언트 실경기 검증

2026-11-13, 같은 Windows PC의 실제 Unity 개발 플레이어 두 개와 로컬 API/관리자 서버, Photon을 사용했다. 연습 경기 경로 대신 일반 Pavilion 경기 경로를 사용하되 개발용 Photon 버전과 임시 경기장으로 다른 사용자와의 매칭을 분리했다.

최종 실행 `f5c331f996c4` 통과. 경기 ID는 `8887b377e6f346bea88f084b4c60d352`, 빌드는 `PracticeMatchTest-20261113-113526`이다. 양쪽 보고서 `Ok=true`, Surrender 정산, 종료 후 4초 관찰 및 예외 로그 검사, 화면 8장 검사, 임시 경기장/계정 정리까지 완료했다. 증거는 `Logs/EquipmentE2E/f5c331f996c4/`에 저장했다.

실제 판매 중인 상품을 새 테스트 계정별로 구매·장착했다. 서로 다른 Bandana/Silver 캐릭터와 서로 다른 메시지 묶음을 선택했다. 일반 회원의 지갑·장착 정보는 변경하지 않았다.

## 확인 항목

- 로그인 화면을 통한 실제 인증, 로비 접속, Photon 방 입장과 일반 경기 시작.
- 두 클라이언트가 같은 경기 ID와 같은 서버 장비 스냅샷을 받는지 확인.
- 양쪽 경기 UI Image의 실제 Sprite가 장착한 캐릭터 리소스와 일치하는지 확인하고 1280×720 화면 캡처.
- 실제 메시지/표정 버튼으로 각자의 첫 장착 메시지와 환희 감정을 송신. 본인 및 상대 UI의 텍스트·활성 상태·Sprite를 검사.
- 각 클라이언트가 자기 차례에 기존 샷 애니메이션과 물리·Photon 전송 경로로 샷 실행. 강제 득점·턴 변경·공 재배치는 하지 않음.
- 실제 샷의 충격량, 타격점, 팔로스루를 양쪽에서 기록하고 비교. 네트워크 수치 양자화를 고려한 허용 오차 적용.
- 각 큐대의 파워/팔로스루 기대값, 턴 제한, 당점 UI 경계와 실제 공 이동·정지 및 자동 표정 반응 확인.
- 정상 기권으로 종료한 뒤 양쪽의 서버 Surrender 정산 확인.

첫 화면 검증 중에는 숨긴 Unity 창의 캡처가 검게 나와 표시 창으로 재실행했다. 화면이 실제로 렌더링됐는지도 검사한다. 종료 직후 `PopNoticeMsg`의 지연 콜백이 파괴된 UI를 접근하는 예외를 발견해, 파괴 시 취소 토큰과 참조 검사를 추가했다. 수정본에서는 완료 후 4초를 더 관찰하고 예외 로그도 검사한다.

## 재현

1. 로컬 API 5080과 관리자 5082를 실행한다. 로컬 개발 관리자 로그인과 PostgreSQL 설정이 필요하다.
2. Unity의 `Tools > Magic Online > New Match Test > Build Windows Test Player`로 최신 개발 빌드를 만든다.
3. `python Server/GameApi/Run-EquipmentE2E.py`를 실행한다. Python의 requests, beautifulsoup4, psycopg, Pillow가 필요하다.

개발 빌드의 `-equipment-match-e2e`를 명시한 경우에만 테스트 자동화가 활성화된다. 일반 실행과 출시 빌드에는 자동 로그인·샷 실행이 적용되지 않는다. 로그인 정보는 오케스트레이터 메모리와 자식 프로세스 환경으로만 전달하며 보고서·명령줄에 저장하지 않는다.

실행별 `Logs/EquipmentE2E/<실행 ID>/`에 A/B JSON, 플레이어 로그, 기본/메시지/감정/샷 PNG와 결과 JSON을 저장한다. 테스트 종료 후 직접 만든 경기장을 관리자 폼으로 제거하고 테스트 계정은 회원 삭제 확인 폼으로 정리한다. 정산·감사 기록은 보존한다.

검증 범위는 같은 PC의 Windows 네이티브 두 클라이언트와 Resources 이미지다. 모바일, 서로 다른 물리 기기, 외부 CDN 다운로드·장애 상황까지 검증한 것은 아니다.
