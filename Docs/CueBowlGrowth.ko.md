# 큐대 바가지 성장

큐대별로 파워·팔로스루·당점·시간·가이드 바가지를 가진다. 기본 최대값은 20/10/30/20/40이며 관리자 > 상점 > 큐대 편집에서 각각 1~10,000으로 설정한다. 기존 회원의 레벨·성장 진도는 보존한다. 현재 바가지 회차는 시작 당시 최대값을 유지하고 다음 회차부터 최신 상점 최대값을 사용한다.

정상 득점 1점마다 가득 차지 않은 항목 하나를 같은 확률로 골라 +1한다. 뱅크샷 2점은 두 번 배분한다. 가득 찬 항목은 승인 여부와 관계없이 배분 대상에서 제외한다. 모두 가득 차면 추가 득점은 소멸한다. 대기 득점이나 다음 회차로 넘어가는 잔고는 없다. 중복 전송을 막는 이벤트 식별자는 남기므로, 버려진 득점도 마시기 이후 재전송해서 받을 수 없다.

회원 > 사물함 > 큐대 상세에서 각 바가지의 현재값/최대값과 승인 상태 및 상품의 자동 마시기 여부를 확인하고 `마시기`를 누른다. 다섯 항목 모두 승인하면 진도 +1과 함께 바가지를 초기화한다. 진도가 기존 도달 진도에 도달하면 능력치 레벨이 최고 레벨까지 1씩 오른다. 이미 마신 항목은 회차가 끝날 때까지 잠긴다.

자동 마시기는 관리자 상점의 큐대 상품 설정이며 기본 꺼짐이다. 해당 상품을 보유한 모든 회원에게 공통으로 적용하고 회원은 변경할 수 없다. 관리자가 켜면 다음 회원 정보 조회 또는 득점 처리에서 이미 가득 찬 항목도 승인하고 이후 가득 찬 항목을 자동 승인한다. 끄면 다음 조회/득점부터 수동 승인으로 돌아가며 이미 마신 항목의 승인은 유지한다. 마지막 승인 전후 득점과 중복 요청은 회원 지갑 행 잠금 아래 같은 트랜잭션으로 처리한다. 성장 후 성능은 기존 규칙대로 다음 경기/연습 입장에서 반영하며 진행 중인 장비 스냅샷은 바꾸지 않는다.

API:

- `POST /api/me/cue-progress/practice`: 기존 득점 보고에 `Points`(1~2, 생략 시 1)를 추가. 연습·친선·길드전 경로에서 사용한다. 일반 대전은 기존 합의 정산의 점수 이벤트에서 지급한다.
- `POST /api/me/cue-bowls/drink`: `CueId`, `Operation`(GUID), `Cycle`, `Index`(0~4). 가득 차지 않았거나 오래된 회차는 409로 거절한다.
- 회원용 `/api/me/cue-bowls/auto` 변경 API는 제거했다. 관리자 상품 편집의 `BowlAuto`를 서버가 읽는다.
- `/api/me/inventory`와 상점 응답의 `CueBowls`: `Maximum`, `Filled`, `Drunk`, `Auto`, `Cycle`.

회원 인증과 보유 큐대 검사를 거치며 다른 회원의 상태는 수정할 수 없다. 관리자 회원 큐대 탭에는 바가지 현황과 자동 마시기 상태를 표시한다. 관리자의 큐대 성장 초기화는 바가지도 초기화하고 회차를 증가시킨다. 이전 득점/승인 식별자는 유지한다.

DB 변경은 `026_cue_bowls.sql`과 상품 자동 마시기 타입을 검사하는 `027_cue_bowl_product_auto.sql`이다. API 시작 시 기존 마이그레이션 경로로 적용한다. 기존 마이그레이션 파일은 수정하지 않는다.

검증:

```powershell
dotnet build Server/GameApi/GameApi.csproj --output Logs/Bowls/GameApi
python Server/GameApi/Run-CueBowlsSmoke.py
```

HTTP 검증은 격리 PostgreSQL 스키마와 임시 서버를 만들고 종료 시 제거한다. 관리자 입력·회원/비회원 권한·무효 득점·수동/자동 승인·설정의 다음 회차 반영·동시 중복 요청을 확인한다. 운영 회원이나 상품을 테스트용으로 수정하지 않는다.

2026-11-24 검증: 큐대 능력치/성장 DB 검사 89개, 바가지 HTTP 검사 23개, 유니티 바가지 상세창 검사 5개를 통과했다. 유니티 런타임 컴파일과 실제 상세창 렌더를 확인했다. 기존 실행 중인 로컬 API/관리자 서버를 새 빌드로 교체했고 두 서버의 DB 연결 및 관리자 페이지 응답을 확인했다. 실제 두 PC 대전 및 Windows 플레이어 빌드는 이번 검증에 포함하지 않았다.

상품 자동 마시기 설정으로 이동한 후 재검증: 성장 DB 89개, HTTP 25개, 유니티 상세창 6개를 통과했다. 관리자의 상품 설정 켜기/끄기가 기존 보유 회원에게 반영되고, 회원용 자동 마시기 변경 API와 버튼이 제거된 것을 확인했다.
