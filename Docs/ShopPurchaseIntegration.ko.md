# 보석으로 상점 상품 구매

작성일: 2026-11-12

## 동작

Unity 상점에서 큐대·캐릭터·메시지 상품을 누른 뒤 `보석으로 구매` → 가격 확인 → `구매 확정`으로 구매한다. 구매 후 해당 상품은 `보유 중`으로 표시되고 재구매 버튼이 사라진다. 보석 팩의 현금 결제와 구매한 상품의 장착은 이번 구현에 포함하지 않는다.

기존 테스트 상품 중 큐대·캐릭터·메시지 9개는 관리자 상품 수정 화면을 통해 판매 허용으로 변경했다. 보석 팩은 현금 결제가 구현되지 않았으므로 보석 구매 대상에서 제외한다. 실제 사용자의 보석 잔액을 테스트 목적으로 변경하지 않았다.

## API

`POST /api/shop/purchases` — 게임 계정 인증 필요.

```json
{
  "RequestId": "00000000-0000-0000-0000-000000000001",
  "ProductId": 8,
  "ExpectedPriceGem": 100,
  "ExpectedRevision": 2
}
```

응답은 `PurchaseId`, `ProductId`, `PaidGem`, `BalanceGem`, `AlreadyProcessed`를 포함한다. 상품 목록 API는 로그인 사용자에 해당하는 `Owned`도 제공한다.

서버는 다음 순서로 처리한다.

1. 인증 사용자 지갑을 행 잠금으로 잠근다. 다른 재화 처리와 같은 잠금을 사용한다.
2. 같은 사용자의 RequestId로 완료한 구매가 있으면 기존 영수증을 반환한다. 다른 상품·가격으로 재사용한 요청은 거부한다.
3. 상품 행을 공유 잠금으로 읽고 상품 종류, 공개 여부, 판매 허용, 판매 기간, 가격 및 수정 버전을 확인한다.
4. 중복 보유와 보석 부족 여부를 확인한다.
5. `wallets.jem` 차감, `shop_user_inventory` 추가, `shop_purchases` 영수증, `wallet_ledger`의 `Shop:<RequestId>` 원장을 하나의 트랜잭션에 저장한다.

오류가 발생하면 모두 취소한다. 무료 상품은 보석 0개로 지급하며 원장과 영수증을 남긴다. 이미 완료한 요청의 재확인은 이후 가격·판매 상태가 바뀌어도 기존 영수증을 반환한다. 응답의 잔액은 재확인 당시의 현재 잔액이다.

## Unity의 재요청 처리

- 구매 확정 후 요청 ID와 가격·버전을 API 주소 및 사용자별 PlayerPrefs 키에 저장한 다음 전송한다. 인증 토큰은 이 기록에 포함하지 않는다.
- 전송 중에는 다른 구매를 시작하지 않는다.
- 통신 실패 또는 서버 오류처럼 성공 여부가 불분명하면 요청을 보존한다. 상점의 `구매 결과 확인` 버튼은 같은 요청 ID로 다시 확인한다.
- 미확인 구매가 있으면 새 구매보다 해당 요청을 먼저 확인한다. 앱 재시작 후에도 기록을 읽는다.
- 성공 또는 명확한 구매 거부가 확인되면 요청 기록을 지운다.
- 구매 완료 후 보석 잔액을 갱신하고 상품을 보유 상태로 표시한다.
- 서버 가격·버전이 바뀌면 구매를 거부하고 새로고침 및 재확인을 안내한다. 화면의 가격과 다른 금액으로 자동 구매하지 않는다.

## 검증

### 실제 PostgreSQL 격리 검사

`Server/ShopPurchase.Tests`는 임시 스키마에서 실행하고 종료 시 해당 스키마를 정리한다. 실제 사용자 지갑과 상품은 수정하지 않는다.

```powershell
dotnet build Server/ShopPurchase.Tests/ShopPurchase.Tests.csproj --output "$env:TEMP/MagicOnline2-ShopPurchaseVerified"
dotnet "$env:TEMP/MagicOnline2-ShopPurchaseVerified/ShopPurchase.Tests.dll"
```

39개 검사 통과: 세 종류 지급, 동일 요청 동시 실행의 단일 차감, 서로 다른 요청의 중복 보유 방지, 서로 다른 상품의 동시 과소비 방지, 보석 부족, 무료 상품, 비공개·판매 중지·기간 제한, 가격·버전 변경, 요청 ID 재사용 충돌, 구매 후 판매 상태 변경의 영수증 재확인, 마지막 원장 쓰기 실패 시 전체 롤백, 같은 요청의 실패 후 재시도 및 사용자별 보유 분리.

### 실제 HTTP 검사

별도의 검증용 게임 계정을 만들고 해당 계정에만 테스트 보석 1,200개를 지급했으며 지급 원장도 기록했다. 큐대·캐릭터·메시지 각 한 개의 요청을 5개씩 동시에 보내 다음을 확인했다.

- 각 상품의 구매·차감·지급은 한 번만 발생하고 나머지는 같은 영수증을 반환한다.
- 세 종류 구매의 합계는 보석 300개이며 검증 계정의 잔액은 900개다.
- 구매 이력 3개와 구매 차감 원장 3개가 일치한다.
- 새 요청 ID로 중복 구매하면 거부한다.
- 구매 계정의 상품만 Owned=true가 되며 다른 계정은 보유하지 않는다.
- 미인증 요청과 보석 부족 계정의 구매를 거부한다.

### Unity

열려 있는 Unity 에디터에서 변경 스크립트 컴파일을 확인했다. `Tools > Local Game API > Verify shop purchase UI`는 미리보기 씬에 검사용 UI를 만들고 상품 구매 버튼, 보유·판매 중지에 따른 버튼 숨김, 종류별 목록, 페이지 이동, 상세 및 빈 목록 처리를 검사한다. 실제 계정 생성이나 구매 요청은 수행하지 않는다.

이미지 파일은 기존 테스트 경로를 유지한다. 구매 성공이 실제 이미지 제공이나 장착 적용을 의미하지는 않는다.
