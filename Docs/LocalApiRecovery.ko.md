# 결과 파일 손상 및 통신 장애 복구

2026-10-18. 앞선 결과 조작·계정 격리 검증은 `LocalApiResultGuard.ko.md`에 기록했다.

## 저장과 복구

`MatchResultJournalStore`가 사용자·API 주소별 기존 결과 파일을 저장한다. 기존 `Writes` 형식은 읽을 수 있고, 새 저장부터 버전·저장 순서 번호·SHA-256 체크섬을 추가한다. 임시 파일을 디스크에 flush한 뒤 원자적으로 교체하고, 같은 최신 내용을 `.bak`에도 저장한다.

시작할 때 본문·임시 파일·백업·백업 임시 파일을 검증해 저장 순서 번호가 가장 큰 정상본을 선택한다. 파일 시각에 의존하지 않는다. 이미 비운 최신 큐보다 오래된 백업을 선택해 정산 요청이 다시 나타나지 않게 한다. 손상된 파일은 `.corrupt-<시각>-<식별자>`로 보관하며 정상본을 복구한다. 잠금·접근 오류는 파일 손상으로 분류하지 않고 재시도한다. 더 새로운 형식의 파일은 덮어쓰지 않고 새 클라이언트가 필요하다는 오류로 유지한다.

모든 저장본이 손상되면 원본들을 별도 보관하고 새 큐를 만든다. 이전 결과를 복구하지 못했다는 경고 로그와 상태 문구를 남긴다. 이 경우 손실된 점수나 승패를 임의로 만들어 전송하지 않는다. 서버 정산 기록과 별도 확인이 필요하다. 체크섬은 우발적 파일 손상 검사이며 사용자가 변경한 클라이언트의 결과를 증명하는 수단은 아니다.

## 통신 복구

대기 요청을 다시 보낼 때 서버 경기 상태를 먼저 확인한다. 연결이 끊긴 동안 서버가 이미 정산했다면 해당 영수증을 적용하고 큐를 비우며, 로컬 결과나 기권으로 판정을 바꾸지 않는다. 결과 불일치가 있으면 서버 확인을 기다린다. 특정 요청의 400·403·404·409 오류는 해당 요청을 보존하면서 다른 결과의 처리를 계속한다. 연결 실패·서버 장애는 기존 재시도 루프로 돌아간다.

## 검사

Unity의 `Tools > Local Game API > Validate result journal recovery` 또는 개발 빌드 전 검사로 실제 `JsonUtility`와 파일 시스템을 사용한다. 2026-10-18, 다음 12개 검사를 통과했다.

- 기존 파일 형식 읽기, 최신 백업의 본문 손상 복구, 저장 도중 남은 최신 임시 파일 복구.
- 큐를 비운 후 오래된 백업으로부터 요청이 재등장하지 않음.
- 모든 사본 손상 시 4개 원본 보관과 확인 경고.
- 잘못된 경기 ID, 누락된 Writes, 점수·승자 모순의 정상 백업 복구.
- 본문 유실 시 백업에서 재생성, 파일 잠금 시 원본 보존·재시도.
- 미래 버전 원본 보존, JSON 형식을 유지한 값 변경의 체크섬 탐지.

실행 결과: `UserSettings/MatchResultJournalValidation.json`의 `Ok=true`, `Checks=12`.

두 실제 개발 플레이어를 실행하는 통합 검사는 다음 명령으로 실행한다.

```powershell
./Server/GameApi/Run-ClientE2E.ps1 -Mode corrupt
./Server/GameApi/Run-ClientE2E.ps1 -Mode outage
```

`corrupt`는 실제 경기 종료 결과를 파일에 저장한 후 본문을 손상시키고 앱을 종료한다. 같은 계정의 새 프로세스가 백업에서 결과 1건을 복구하고 손상 원본을 보관한 뒤 정상 정산·큐 0건을 확인한다.

`outage`는 실제 타격 이후 양쪽 Photon 송수신 패킷 손실을 100%로 설정하고 개발 전용 HTTP 요청 실패를 함께 주입한다. 55초 동안 기권 요청을 파일 큐에 보존한다. 서버의 생존 신호 만료 정산 이후 통신을 복구해 `BothDisconnected`, 입장료 반환, 큐 비우기 및 전적 미반영을 확인한다. 이 검사는 클라이언트 전송 경로의 장애 주입이다. 실제 네트워크 어댑터·공유기·운영체제 장애, 두 물리 기기의 동작은 별도 검증 대상이다.

두 검사 모두 실제 물리 타격을 수행했고 양쪽 보고서 `Ok=true`로 완료됐다. 손상 복구는 `JournalRecovered=true`, `CorruptCopies=1`, 대기 결과 1→0건과 `MutualConfirmation`을 확인했다. 장애 검사는 양쪽 `SawOffline=true`, `PendingDuringOutage=1`, 복구 후 `BothDisconnected`를 확인했다. 네 계정 모두 최종 코인 30이었다. 장애 검사 보고서의 기존 `PendingAfterRestart` 필드는 재시작 없는 이 모드에서도 복구 후 큐 수를 기록하며 값은 0이다.

계정 격리 회귀 검사에서 C의 큐는 0건이고 원래 경기 조회 404·결과 제출 403이었다. A로 돌아오면 결과 1건이 보존됐으며 재전송 후 0건이 됐다. 저장 방식 변경 후에도 다른 계정의 파일을 보내지 않았다.

PostgreSQL에서 세 경기 모두 분쟁 없이 `Applied`이며 경기당 영수증 1개·공통 기록 1개·개인 기록 2개·입장/정산 원장 4개를 확인했다. 정상 무승부 두 경기의 참가자에게 해당 종목 무승부만 1회씩 반영됐다. 통신 장애 경기 참가자와 계정 격리의 C에게는 승패·무승부를 반영하지 않았다. 총 7계정 모두 코인 30과 원장 합계가 일치했다.

최종 검사 도구는 서버 정산과 양쪽 로컬 큐 저장 완료를 모두 기다린 뒤 성공으로 판정한다. 초기 검사에서 서버 정산 직후 상대 프로세스가 큐 저장 완료 전에 종료될 수 있던 검사 종료 조건을 보강했다. 최종 세 실행이 끝난 뒤 참가자 6명의 본문·백업 총 6쌍을 직접 읽어 대기 요청 0건, 두 사본 동일, 체크섬 정상임을 확인했다. 클라이언트 로그에 처리되지 않은 예외는 없었다.

각 실행 원본은 `Logs/LocalApiE2E/<실행 ID>/`에 보관한다. 최종 보고서·DB 대조·본문/백업 검증 근거는 [LocalApiRecovery.results.json](LocalApiRecovery.results.json)에 보관한다. 실제 어댑터·공유기 장애 및 두 물리 기기의 검증은 위 검사 범위와 구별한다.
