# 연습당구 기반 3구·4구 대전 전환 개발 계획

작성일: 2026-09-23  
대상: MagicOnline2 / Unity 6000.5.7f1  
문서 상태: 현재 소스 조사에 근거한 설계안. 이 문서 작성으로 대전 전환이 구현된 것은 아니다.

## 1. 목표와 개발 범위

현재의 로그인 → 경기장 선택 → 매칭 대기 흐름을 유지하고, 두 사람이 매칭되면 기존 Pavilion 경기 대신 연습당구의 TableSet07 기반 3구 또는 4구 대전을 시작한다. 연습에서 개선한 타격감, 파워·팔로스루·당점, 공의 움직임, 점수 연출을 대전에서도 사용한다.

사용자 확정 요구사항: 연습 3구·4구와 대전을 모두 이용할 수 있어야 한다. 연습 메뉴를 대전 메뉴로 대체하지 않는다. 단계별 실제 적용·검증 상태와 개발 전 백업은 [진행 기록](MultiplayerDevelopmentProgress.ko.md)에 기록한다.

첫 목표는 두 클라이언트에서 동일한 경기 상태로 끝까지 진행되는 일반 대전이다. 코인과 전적이 걸리는 정식 대전은 결과 검증과 중복 정산 방지까지 갖춘 후 연다. 기존의 마무리 미션·서바이벌·아이템은 별도 이식 대상으로 관리하며, 기본 3구·4구 완성 전에 모두 가져오지 않는다.

이 문서의 ‘확인’은 소스에서 확인한 사실이고, ‘위험’은 그 구조에서 예상되는 실패 가능성이다. 서버 내부 권한 설정, 실제 변조 공격, 여러 기기에서의 장시간 대전은 이번 조사에서 검증하지 않았다.

## 4. 권장 구조

### 4.1 역할 분리

- MatchSession: 매칭부터 종료까지의 상태, 참가자 Actor와 좌석, matchId, 현재 턴을 관리한다.
- MatchConfig: HallIdx, 종목, 목표점수, 쿠션 조건, 제한시간, 마무리 규칙, 물리·규칙·통신 버전을 담는다. 양쪽 합의 후 경기 중에는 바꾸지 않는다.
- PracticeMatchAdapter: TableSet07의 물리·큐·UI를 세션과 연결한다. 기존 Pavilion용 PoolNetMsg와 분리한다.
- MatchRules: 충돌 기록을 받아 샷 종료 시 득점·감점·턴·승패를 산출한다. UI와 통신에 의존하지 않는다.
- MatchTransport: Photon 메시지 전송, 발신자·식별자 검사, 재전송·중복 제거를 담당한다.
- MatchPresentation: 상대 조준, 공 움직임 보간, 점수·알림·결과 표시를 담당한다. 점수 판정을 독자적으로 실행하지 않는다.

권장 상태 흐름:

`Lobby → Joining → WaitingOpponent → Configuring → Loading → Ready → Aiming → Simulating → Resolving → Aiming / Finished → Leaving`

연결 문제가 생기면 `Reconnecting`으로 진입한다. 상태마다 허용 입력과 제한시간을 정하고, 늦게 도착한 이전 상태 메시지는 무시한다. 연습 실행은 네트워크 없이 기존 기능을 유지한다.

### 4.2 물리와 판정의 기준

초기 구현은 한 클라이언트(방장)를 물리·판정 기준으로 삼는 방식이 현실적이다. 타격자는 파워·팔로스루·당점·큐 방향을 담은 요청을 보내고, 기준 측은 턴과 입력 범위를 검사한 뒤 연습 물리를 실행한다. 상대는 위치·회전 스냅샷을 보간하여 표시한다. 양쪽에서 같은 입력으로 계산해도 결과가 항상 일치한다고 가정하지 않는다.

첫 구현에서는 기준 측과 관전자 화면을 먼저 맞추고, 지연을 줄이는 로컬 예측은 측정 후 추가한다. 관전자 측 로컬 충돌로 점수를 확정하거나 다음 턴을 열어서는 안 된다. 정지한 뒤에는 최종 공 상태와 확정 점수를 적용하여 오차를 제거한다.

방장은 신뢰할 수 있는 게임 서버가 아니다. 이 구조는 동기화 기준을 제공하지만 방장 변조를 막지 못한다. 코인·랭킹 대전 공개 전에는 서버에서 검증 가능한 입력/결과 경로 또는 서버 권위 시뮬레이션을 마련해야 한다. 현재 Backend 환경이 물리 재검증까지 지원하는지는 별도 조사한다. 단순 결과 해시 비교만으로 부정행위가 차단된다고 보지 않는다.

### 4.3 메시지와 상태 복구

공통 필드: `protocolVersion, matchId, authorityEpoch, turnId, shotId, sequence`. 참가자 식별은 표시용 닉네임 대신 Photon Actor와 인증된 사용자 매핑을 사용한다.

| 메시지 | 내용 | 전달 정책 |
|---|---|---|
| MatchConfig / SceneReady / StartMatch | 설정, 좌석·수구, 로딩 완료, 시작 시각 | 신뢰 전송, 확인 응답, 상태별 중복 무시 |
| AimState | 큐 방향·기울기, 파워·팔로스루·당점 | 최신 값 우선, 전송 빈도 제한 |
| ShotRequest / ShotAccepted | 샷 입력과 승인된 샷 번호·시작 상태 | 신뢰 전송. 승인 전 중복 타격 방지 |
| BallSnapshot | 시각·순번, 공 ID별 위치·회전·속도·회전속도 | 순서 확인 후 보간. 주기·대역폭은 실측 조정 |
| ShotResolved | 파울 원인, 점수 변화, 최종 공 상태, 다음 턴, 승패 | 한 번만 적용. 누락 시 재요청 |
| MatchEnded / ResultReceipt | 종료 원인과 최종 결과, 정산 수신증 | matchId 기준 중복 처리 방지 |

재접속 시에는 MatchConfig, 확정 점수, 턴, 공 상태, 마지막 확정 shotId, 타이머 기준을 함께 복원한다. 진행 중 샷을 복구할 수 없는 경우 판정 전 상태로 임의 재개하지 않는다. 초기 버전에서는 기준 측 이탈 시 무효 종료하는 정책을 권장하며, 방장 이전은 별도 검증 후 지원한다. 정식 대전에서는 악의적 이탈로 패배를 회피하지 못하도록 서버 정책이 필요하다.

## 5. 경기 규칙과 UI 적용 기준

### 5.1 공통 규칙

- 3구는 현재 연습 구현을 기준으로 두 목적구와 필요한 쿠션 조건을 검사한다. 정확한 쿠션 인정 순서와 특수 상황은 충돌 기록 테스트로 고정한다.
- 4구는 상대 수구 접촉 또는 적구를 하나도 맞히지 못하면 감점한다. 적구 하나만 맞히고 상대 수구를 맞히지 않은 경우는 무득점이다.
- 4구에서 적구 두 개를 맞혀도 즉시 점수를 확정하지 않는다. 모든 공이 멈춘 후 상대 수구 접촉까지 포함하여 판정하며, 파울이 득점보다 우선한다.
- 한 샷에서 파울 사유가 여러 개여도 감점은 한 번만 적용한다. 현재의 0점 하한을 유지하는 것을 기본안으로 한다.
- 득점 시 턴 유지, 무득점·파울 시 턴 교대를 기본안으로 하되 기존 마무리·서바이벌 규칙과 섞지 않는다.
- 마지막 목표점수 도달 샷도 최종 판정 후 승리를 확정한다. 제한시간 만료 중 움직이는 샷의 인정 여부는 별도 정책으로 확정한다.

### 5.2 연습 전용 기능의 격리

대전 중에는 되돌리기, 자유 공 배치, 점수 초기화, 임의 재시작, 물리 옵션 변경, 리플레이 되감기를 UI와 명령 처리 양쪽에서 막는다. 경기 중 리플레이 저장은 허용할 수 있지만 실제 경기 상태는 변경하지 않는다. 가이드는 경기장 설정에 따라 양쪽 동일하게 적용한다.

승패 팝업은 로컬 플레이어 기준으로 ‘승리/패배/무효’를 표시한다. 연습의 3초 후 연습 메뉴 복귀를 대전에 그대로 적용하지 않는다. 대전 결과 화면에서 재대전 또는 경기장 복귀를 제공하는 것을 기본안으로 한다. EggBox 0.5초 이동은 확정 결과를 받은 뒤 한 번만 실행한다.

## 6. 개발 단계와 완료 기준

| 단계 | 작업 및 산출물 | 완료 기준 |
|---|---|---|
| 0. 기준 확보 | 기존/연습 기능 목록, 재현 로그, 현재 빌드 보관, 비밀번호 로그 제거, kr와 버전 진단 | 에디터+빌드 및 빌드+빌드에서 같은 지역 확인. 민감정보 없이 매칭 실패 원인 추적 가능 |
| 1. 로컬 구조 분리 | 실행 모드·종목 분리, MatchConfig, 공통 규칙, PracticeMatchAdapter와 주입 초기화 | 기존 연습 3구·4구·리플레이 검증 통과. 온라인 초기화에서 Player 1/2와 7점 고정값이 실제 설정을 덮어쓰지 않음 |
| 2. 매칭 안정화 | 서버 기준 경기장 필터 매칭, 실패·취소·타임아웃, 단일 대기실 세션 | 동시 입장과 늦은 목록에서도 두 사람 매칭. 다른 종목/버전은 매칭되지 않음. 실패 시 무한 대기 없음 |
| 3. 새 경기장 진입 | 양쪽 설정 합의, 좌석/수구 결정, TableSet07 로딩, SceneReady와 StartMatch | 로딩 속도가 달라도 양쪽 준비 전 타격 불가. 경기 시작은 한 번만 발생 |
| 4. 한 샷 동기화 | ShotRequest 승인, 입력 범위 검사, 기준 측 시뮬레이션, 관전자 보간, 최종 스냅샷 | 양쪽에 동일한 샷·최종 공 위치가 표시. 상대 턴 입력과 중복 샷이 거절됨 |
| 5. 경기 완주 | 3구·4구 판정, 점수·턴·시간·승패, EggBox 및 알림 연결 | 양쪽 점수·턴·승자가 모든 샷에서 일치. 마지막 득점 뒤 늦은 파울도 정확히 처리 |
| 6. 종료·복구 | 대기 취소, 기권, 일시 끊김, 재접속, 기준 측 이탈, 늦은 메시지 차단 | 끊김·나가기 후 입력 잠금과 결과가 일치. 이전 경기 메시지로 새 경기 상태가 바뀌지 않음 |
| 7. 결과·재대전·리플레이 | 결과 화면, 새 matchId 재대전, 대전 샷 저장, 검증된 정산 경로 | 재대전이 초기 상태로 시작. 결과 재전송에도 보상/전적 1회 반영. 저장 재생이 실경기와 분리 |
| 8. 공개 검증 | 두 실제 클라이언트, 지연·손실·저사양·해상도·장시간 테스트, 새 Windows 빌드 | 아래 시험표 통과 및 미해결 P0 없음. 코인 대전은 서버 검증 완료 후 허용 |

선행 관계는 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8이다. 화면만 먼저 연결한 상태를 대전 완성으로 보지 않는다. 구현 기간은 단계 4의 물리 동기화 실측과 서버 검증 방식이 정해진 후 산정한다.

## 7. 필수 시험표

| 시험 | 기대 결과 |
|---|---|
| 3구 두 계정 / 4구 두 계정 매칭 | 같은 경기장에 두 사람 입장, 설정 일치 |
| 두 클라이언트 동시 입장, 빈 방 생성 경합 | 불필요한 분리 대기 없이 매칭 또는 명시적 재시도 |
| 경기장·프로토콜·물리 버전 불일치 | 시작 차단, 사용자에게 업데이트/선택 안내 |
| 대기 중 취소, 카운트다운 중 상대 종료 | 카운트다운 중단, 늦은 시작 메시지 무시 |
| 한쪽 로딩 지연/실패 | 준비 전 입력 차단, 제한시간 후 복귀 |
| 상대 턴 타격, 같은 shotId 재전송, NaN/범위 밖 파워·공 ID | 승인하지 않고 현재 상태 보존 |
| 4구 적구 0개 / 1개 / 2개 / 적구 2개 후 상대 수구 | 각각 감점 / 무득점 / 득점 / 감점. 모두 정지 후 확정 |
| 0점에서 파울, 마지막 목표점수 후보 후 파울 | 점수 하한 유지, 잘못된 승리 없음 |
| 3구 쿠션 부족·충족·접촉 순서 경계 | 합의한 규칙표와 일치 |
| 샷 중 시간 만료, 동시에 종료 메시지 도착 | 정한 정책에 따라 단일 판정·단일 종료 |
| 지연 50/150/300ms, 손실 1/5%, 메시지 중복·순서 역전 | 영구적인 점수/턴 불일치 없음. 복구 불가 시 명시적 종료 |
| 조준 중/샷 중/판정 직후 연결 끊김 | 정책에 맞게 유예·복구·종료, 중복 득점 없음 |
| 방장 종료, 재대전 후 이전 샷 도착 | 무효/복구 정책 적용, 이전 경기 메시지 무시 |
| 결과 응답 지연·재시도·앱 재시작 | 코인·전적 중복 반영 없음 |

| 새 빌드 d3d11 실행 | UberFX 컴파일 오류 없음, 양쪽 네트워크 설정 일치 |

네트워크 품질 수치는 초기 시험 조건이지 성능 보장치가 아니다. 위치 허용 오차·화면 지연·대역폭의 합격 수치는 단계 4에서 당구대/공 크기와 실제 기기 측정에 맞춰 정한다. 점수·턴·승패·최종 공 상태 버전은 오차 없이 같아야 한다.

## 8. 개발 전 확정할 운영 정책

다음은 사용자 결정이 필요한 정책이며 아직 구현 약속으로 간주하지 않는다.

1. 초기 공개를 무료 일반 대전으로 할지, 코인·전적을 포함할지.
2. 선공을 무작위·번갈아·별도 선공 결정 중 무엇으로 정할지. 현재 방장 고정은 테스트 동작이다.
3. 전체 제한시간 종료 시 진행 중 샷 인정, 동점·무승부 처리.
4. 일시 끊김 유예시간, 기권·앱 종료·기준 측 이탈의 승패 및 환불 처리.
5. 마무리 미션·서바이벌·아이템과 조준 가이드의 적용 범위.
6. 대전 결과 표시 시간, 경기장 복귀 및 재대전 UX.

정책 확정 전에도 단계 0~4의 구조 분리·매칭·한 샷 동기화는 진행할 수 있다. 임시 정책은 MatchConfig에 명시하고 양쪽이 동일하게 사용해야 한다.
