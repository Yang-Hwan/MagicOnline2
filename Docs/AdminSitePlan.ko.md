# MagicOnline2 관리자 사이트 개발 기획서

작성일: 2026-10-18 · 기획안 v1 · 대상: Android·iOS 게임 운영

이 문서는 개발 제안이다. 관리자 사이트·관리자 API·결제 기능이 현재 구현되었다는 의미는 아니다.

## 1. 목표와 범위

회원, 경기장 규칙, 대전 및 정산, 재화, 모바일 결제를 한 사이트에서 조회하고 운영한다. 회원 → 경기 → 정산 영수증 → 재화 원장 → 결제 주문을 연결하여 장애와 문의의 원인을 추적한다.

운영자용 PC 웹을 우선하고 태블릿 조회를 지원한다. 일반 사용자의 웹 회원가입·웹 상점은 초기 범위에 포함하지 않는다. 결제 상품은 우선 일회성 재화 상품을 가정한다. 구독·패스·정기 보상은 상품 정책 확정 후 별도 단계로 다룬다.

### 현재 시스템에서 재사용할 부분

- ASP.NET Core GameApi, PostgreSQL, Unity 및 Photon PUN 구조.
- 회원·세션·지갑·3구/4구 전적·차트·출석 자료.
- 경기 등록/준비/생존 신호/분쟁 상태 및 정산 서비스.
- 정산 영수증, 상세 경기 기록, 재화 원장.
- 경기 규칙 계약 버전 1 구현. 실행 서버 적용과 새 플레이어 검사는 별도 잔여 작업이다.

### 추가 개발할 부분

- 관리자 인증·권한·운영 이력과 관리자 전용 API 및 화면.
- 차트 편집/검증/버전/배포, 기간 제재, 보상 업무.
- 경기 이벤트와 장애 검색, 분쟁 처리 절차.
- 모바일 상품·주문·구매 검증·지급·환불 반영.
- 접속 및 집계 지표, 알림, 공지·점검 기능.

## 3. 화면 공통 구성

- 왼쪽 메뉴, 상단 운영/개발 환경 표시, 기간 선택, 마지막 갱신 시각.
- 목록은 검색·필터·정렬·서버 페이지 처리·상세 이동을 제공한다.
- 회원 UUID, 경기 ID, 주문 ID, 원장 요청 키를 서로 연결한다.
- 시각은 화면에서 한국 시간으로 표시하고 DB에는 UTC를 저장한다.
- 원장·재화는 정수로 처리하고 웹 화면에서 큰 정수의 자릿수가 손실되지 않도록 API에서는 필요한 값을 문자열로 전달한다.
- 내보내기는 현재 필터를 적용한다. 대용량은 비동기 작업, 다운로드 만료 및 접근 기록을 둔다.
- 변경 화면에는 변경 전/후, 영향 범위, 처리 사유, 처리 결과를 표시한다. 충돌 시 다른 운영자의 변경을 덮어쓰지 않고 다시 읽도록 한다.
- 조회 전용 권한에는 변경 동작을 표시하지 않으며 서버도 권한을 다시 검사한다.

## 4. 회원 관리

### 회원 목록

검색: UUID, 로그인 ID, 닉네임. 필터: 가입일, 정상/제재 상태. 최근 접속일·플랫폼·앱 버전은 새 접속 이력 수집 이후 제공한다.

표시: 회원 식별자, 닉네임, 가입일, 이용 상태, Coin/Jem, 3구/4구 전적. 비밀번호·인증 토큰은 화면과 내보내기에 포함하지 않는다.

### 회원 상세 탭

1. 기본 정보: 프로필, 계정 상태, 운영 메모.
2. 대전: 종목별 전적과 최근 경기, 분쟁 연결.
3. 재화: 잔액, 입출금 내역, 지급/회수 근거.
4. 결제: 플랫폼별 주문 및 지급/환불 상태.
5. 접속/제재: 로그인 실패, 세션 폐기, 제재 기간/사유/해제 이력.
6. 고객 지원: 문의·신고·처리 메모.

지원 업무: 기간/영구 제한·해제, 세션 강제 폐기, 닉네임 조정, 보안 복구 절차 연결. 이용 제한이 진행 중 경기의 기권을 뜻하지 않도록 분리하고 기존 서버의 경기 만료/정산 정책을 유지한다.

현재 `users.disabled`는 사용할 수 있지만 기간 제재·사유·이력과 접속 정보는 추가 구현이 필요하다.

## 5. 차트 관리

### 관리 대상

- SkillMatch: 경기장 번호/이름, 3구·4구, 목표 점수, 쿠션, 경기 시간, 마무리 미션, 입장료, MaxCoin.
- Attendance: 기간/일차별 보상 종류·수량.
- CommonCode: 코드·값·설명. 숫자/문자열 등 예상 자료형과 사용처를 정의한다.

### 변경 흐름

`현재 배포본 → 초안 작성/CSV 가져오기 → 검증 → 차이/영향 미리보기 → 배포 → 배포 이력`

- 행 편집과 CSV 가져오기/내보내기. 가져오기는 미리보기 후 전체 검증을 통과해야 반영한다.
- 코드 중복, 누락 필드, 자료형/범위, 참조 관계, 지원하지 않는 경기 규칙을 검증한다.
- 스키마 버전, 차트 수정 번호, 규칙 계약 버전을 구분한다. 단순 입장료 변경마다 클라이언트 프로토콜 버전을 올리지 않는다.
- 초안은 배포본과 분리하고 배포는 차트 묶음을 원자적으로 교체한다. 기준 수정 번호가 달라졌으면 충돌로 거절한다.
- 되돌리기는 과거 내용을 복제한 새 수정본을 배포하는 방식으로 기록한다.
- 등록된 경기는 기존 규칙 스냅샷을 유지하고 새 경기는 새 배포본을 따른다.
- 과거 차트만 받은 플레이어는 새 경기 시작 시 규칙 갱신 안내를 받는다. 자동 차트 새로고침 UI는 후속 개선이다.

## 6. 대전 결과 및 로그

### 목록/상세

검색: 경기 ID, 참가자 UUID/닉네임. 필터: 기간, 3구/4구, 경기장, 등록/진행/정산 완료, 결과 불일치, 종료 사유.

상세에는 참가자, 시작/종료, 규칙 계약과 차트 수정 번호, 각 참가자의 결과 보고, 생존 신호 시각, 최종 점수/승자, 정산 사유/영수증, 입장료/지급 원장을 연결한다.

`정산 대기`, `결과 불일치`, `연결 만료`, `규칙 불일치`는 각각 조회할 수 있게 한다. 현재 matches의 상태/보고/생존 신호와 영수증은 재사용한다. 전체 사건 타임라인은 새 이벤트 수집부터 제공한다.

### 기록 종류

| 기록 | 내용 |
| --- | --- |
| 경기 사건 | 등록, 준비, 시작, 연결 만료, 결과 보고, 정산, 규칙 거절 |
| 재화 원장 | 입장료, 정산, 출석, 결제, 운영 보상/회수 |
| 시스템 오류 | API/작업 실패, 상관관계 ID, 재시도 상태 |
| 관리자 감사 | 누가 어떤 자료를 어떤 이유로 변경했는지 |

생존 신호의 매 요청과 모든 물리 프레임을 영구 저장하지 않는다. 반복 장애는 집계하고 진단용 세부 기록은 보관 기간을 별도로 둔다. 경기 리플레이는 현재 데이터만으로 만들 수 없으므로 별도 입력/물리 기록 설계가 필요하다.

### 분쟁 처리

`접수 → 근거 확인 → 처리안 작성 → 승인 → 적용/보류 → 처리 종료`

이미 발급한 최종 영수증·원장 행을 수정하거나 일반 결과 API를 재실행하지 않는다. 운영 보정은 원경기를 참조하는 별도 보정 건으로 기록한다. 미정산 분쟁의 최종 처리도 서버 업무 API에서 경기/지갑 잠금과 유일 처리 키를 적용한다. 보정이 승패 전적에 미치는 정책은 구현 전 확정한다.

## 7. 재화 운영

- Coin/Jem 변동을 회원, 기간, 출처, 경기/주문/운영 처리 건별로 검색한다.
- 현재 잔액과 원장 누계를 비교하고 불일치 건을 표시한다.
- 지급/회수는 회원·재화·수량·사유·관련 문의를 입력하고 처리 전후를 확인한다.
- 동일 처리 건을 재요청해도 한 번만 적용한다. 게임 정산·출석·결제와 같은 지갑 잠금/트랜잭션 원칙을 사용한다.
- 잔액 숫자를 직접 덮어쓰는 기능은 제공하지 않는다. 전적도 원인을 추적할 수 있는 보정 업무로 다룬다.
- 대량 지급과 일정 금액 이상의 조정은 작성자와 승인자를 구분할 수 있게 한다. 기준 금액은 운영 설정으로 확정한다.
- 유료 구매분·무료 지급분·소비/환불 관계를 추적할 재화 구분 및 사용 순서 정책을 추가한다. 현재 지갑 합계/기본 원장만으로 이를 모두 판별할 수는 없다.

## 8. Android·iOS 결제 관리

### 상품과 주문 화면

- 공통 상품 코드에 Google Play 상품 ID와 App Store 상품 ID를 연결한다.
- 표시 항목: 상품명, 지급 재화/수량, 보너스, 판매 여부, 상품 수정 번호, 플랫폼별 연결 상태.
- 실제 스토어 상품/가격/통화 설정과 게임 내 상품 노출을 구분한다. 초기에는 스토어 콘솔에서 가격을 설정하고 관리자는 연결/지급 규칙을 관리한다.
- 주문 검색: 회원, 플랫폼, 스토어 거래 식별자, 상품, 기간, 결제/지급/환불 상태.
- 주문 상세: 구매 근거, 계정 연결, 검증 결과, 지급 원장, 소비/승인 처리, 환불 통지, 재시도 이력.
- 현금 결제 금액은 통화와 함께 정밀하게 저장한다. 국가별 통화 매출을 환산 기준 없이 합산하지 않는다. 스토어 정산 보고서와 수수료/세금 차감 전 주문 금액을 구분한다.

### 결제 처리 구조

`Unity 구매 → 서버에 구매 근거 전달 → 플랫폼 검증 → 주문 확정 + 재화 지급 원장 → 필요한 스토어 후속 처리 → 관리자 조회`

- Google: 구매 토큰과 플랫폼 조회로 검증한다. 주문 ID만으로 중복 지급을 판별하지 않는다. 대기 결제에는 재화를 지급하지 않는다. [공식 보안 안내](https://developer.android.com/google/play/billing/security)
- Apple: App Store Server API와 서명된 거래/서버 통지 V2를 이용하는 구조로 설계한다. [Server API](https://developer.apple.com/documentation/appstoreserverapi), [서버 통지 수신](https://developer.apple.com/documentation/appstoreservernotifications/receiving-app-store-server-notifications)
- 플랫폼별 구매 식별자와 환경에 DB 유일성 제약을 두고 지급과 원장 저장을 같은 트랜잭션으로 처리한다. 구매 근거를 다른 게임 계정에 재사용하지 못하도록 계정 연결을 검증한다.
- 플랫폼 API 호출과 DB를 한 트랜잭션으로 묶을 수 없으므로 후속 처리는 작업 큐/처리 이력으로 재시도한다. 재시도는 이미 완료된 재화 지급을 반복하지 않는다.
- 결제, 검증, 지급, 환불 상태를 별도 필드로 관리한다. 예: 결제 성공이지만 지급 재시도 대기인 주문을 분명히 표시한다.
- Sandbox/테스트 주문을 운영 주문·매출과 분리한다.

### 통지·환불·누락 처리

- Google RTDN과 Apple 서버 통지를 수신하여 중복·순서 역전·재전송을 처리한다. Google RTDN 수신 후에는 Developer API에서 전체 구매 상태를 확인한다. [RTDN 안내](https://developer.android.com/google/play/billing/rtdn-reference)
- 수신 내역, 서명/출처 검증, 처리 상태와 실패 사유를 저장하고 권한 있는 관리자가 처리 재시도를 요청할 수 있게 한다.
- 통지 누락에 대비한 플랫폼 상태 재조회와 주문/원장 대조 작업을 둔다.
- 환불 요청, 스토어의 실제 환불 확정, 게임 재화 회수/미회수 상태를 구분한다. 플랫폼별 가능한 환불 업무와 콘솔 이동을 각각 제공한다.
- 이미 소비한 재화의 환불은 예외 처리 대상으로 둔다. 현재 DB의 음수 잔액 금지 조건을 유지하고 미회수 금액/재화를 별도 건으로 기록한다. 최종 회수·이용 제한 정책은 출시 전에 확정한다.
- 미지급 재처리는 원래 검증된 주문의 지급을 재개한다. 별도 보상은 원주문과 연결하되 결제 지급 성공으로 바꾸지 않는다.
- 카드번호·스토어 비밀번호·비밀 키를 관리자 화면에서 취급하지 않는다. 구매 근거 원문은 접근 제한하며 일반 로그/CSV에서는 마스킹한다.

## 9. 대시보드와 통계

1차 카드: 신규 회원, 경기 등록/진행/완료, 정산 대기/분쟁, 연결 만료, API/DB/작업 상태. 결제 도입 후 지급 대기·환불 미반영·플랫폼별 주문 금액을 추가한다.

최근 API 사용 회원 수는 마지막 활동 수집 기능을 추가한 뒤 제공한다. 이를 Photon의 실제 동시 접속자로 표시하지 않는다. 실제 방/접속 수가 필요하면 Photon 측 관측 수단을 별도로 연결한다.

분석 지표는 정의와 갱신 시각을 표기한다. DAU는 해당 날짜의 실제 게임 활동이 있는 고유 회원으로 정의하고 테스트 계정을 구분한다. 초기에는 일별 가입·경기·종목별 전적·재화 이동을 집계하고 리텐션/결제 전환율은 활동 이벤트 기반이 마련된 뒤 추가한다.

## 10. 관리자 권한과 운영 이력

| 역할 | 허용 범위 |
| --- | --- |
| 최고 관리자 | 관리자/권한 설정, 운영 정책, 민감 작업 승인 |
| 게임 운영자 | 회원/경기 조회, 제재, 차트 초안, 보상 요청 |
| 결제 담당자 | 주문/환불/지급 장애 조회와 허용된 처리 |
| 고객 지원 | 제한된 회원 조회, 문의/신고/메모, 처리 요청 |
| 조회 전용 | 허용된 목록·통계 조회 |

- 개인별 관리자 계정, 별도 관리자 세션, MFA, 세션 만료/폐기. 게임 계정의 토큰으로 관리자 API에 접근할 수 없게 한다.
- 브라우저 인증은 HttpOnly/Secure 쿠키와 변경 요청 위조 방어를 적용한다. 화면 메뉴와 API 권한을 일치시킨다.
- 계정 상태 변경, 차트 배포, 재화 조정, 분쟁 처리, 결제 재시도, 자료 내보내기를 운영 이력에 남긴다.
- 감사 기록: 관리자, 시각, 대상, 동작, 변경 전/후의 필요한 값, 사유, 요청 ID. 비밀번호·토큰·구매 근거 원문은 제외한다.
- 민감 변경 결과와 감사 기록은 함께 커밋한다. 외부 연동은 접수·시도·최종 결과를 연결한다.
- 관리자 화면에서 감사 기록 수정/삭제 기능은 제공하지 않는다. 운영 DB 역할과 보관·백업 권한을 분리한다.

## 11. 시스템 구성과 추가 데이터

기존 C# 자산을 재사용하는 기본안: `Server/AdminWeb`에 ASP.NET Core Razor Pages 기반 관리자 웹을 두고, `Server/GameApi`에 `/api/admin/*` 업무 API를 추가한다. 관리자 인증 검증/권한을 서버에서 공유하고 웹이 DB를 직접 임의 수정하지 않게 한다. 브라우저는 관리자 웹과 같은 출처로 통신하고 관리자 웹이 내부 API를 호출하는 구성을 우선한다. 외부 연동 비밀은 서버 설정에만 둔다.

운영 집계·스토어 후속 처리·예약 배포는 별도 백그라운드 작업으로 수행한다. 화면은 처리 건 ID로 진행 상태를 조회한다. 관리자 장애가 게임 API 전체 중단으로 이어지지 않게 배포·자원·DB 연결 풀을 분리한다.

| 추가 테이블/영역 제안 | 목적 |
| --- | --- |
| admin_users / admin_roles / admin_sessions | 운영자 인증과 권한 |
| admin_audit_logs / operation_requests | 운영 이력과 중복 처리 방지/승인 |
| user_restrictions / user_activity / user_notes | 기간 제재, 활동 수집, 메모 |
| chart_revisions / chart_releases | 초안·검증·배포·되돌리기 |
| match_events / match_cases / match_adjustments | 경기 사건, 분쟁, 보정 |
| wallet_operations / currency_grants / currency_allocations | 운영 조정 및 유료/무료 지급·소비 관계 |
| products / platform_products / product_revisions | 공통 상품과 스토어 연결/지급 조건 |
| payment_orders / payment_events / store_notifications | 검증된 구매, 처리 사건, 통지 |
| payment_grants / refund_cases / background_jobs | 지급 유일성, 환불/미회수, 재시도 |
| announcements / maintenance_settings / daily_metrics | 공지·점검·일별 집계 |

기존 wallet_ledger에는 출처/관련 처리 건 식별 정보를 추가하되 기존 원장을 소급해서 임의 수정하지 않는다. 관련 식별자는 인덱스를 두고 목록 API는 전체 자료를 메모리로 읽지 않는다.

보관 기간은 기록 종류별로 정한다. 현재 일반 경기 상세는 6개월 정리를 사용하므로 관리자 조회에도 반영한다. 분쟁·결제·감사 기록의 기간과 삭제 정책은 운영/개인정보 정책 확정 후 적용하고 운영 화면에 보관 종료 상태를 표시한다.

## 12. 개발 단계와 완료 기준

| 단계 | 개발 산출물 | 완료 기준 |
| --- | --- | --- |
| 0. 기준 확정 | 메뉴/화면 목록, 역할표, 처리 정책, 기존 API 적용 정리 | 개발·운영 환경과 권한/지급/제재 기준 확정 |
| 1. 조회 중심 운영판 | 관리자 로그인/권한, 대시보드, 회원/차트/경기/원장 조회, 감사 기반 | 회원에서 경기·영수증·원장을 연결 조회하고 권한 밖 API 접근 거절 |
| 2. 운영 변경 기능 | 기간 제재, 차트 초안/배포, 보상, 분쟁 처리, 공지/점검 | 변경 사유/이력 보존, 동시 수정 충돌 방지, 반복 요청 단일 반영 |
| 3. 모바일 결제 | 상품/주문, Android/iOS 구매 검증, 지급, 통지, 환불 반영 | 양 플랫폼 테스트 환경에서 구매·앱 종료 후 지급·중복 통지·환불/미회수 경로 확인 |
| 4. 통계와 알림 | 지표 집계, 처리 대기 알림, CSV, 고객 지원 확장 | 지표 정의/원본 대조, 알림 중복 억제, 대용량 조회/내보내기 처리 |
| 5. 운영 배포 | 관리자 HTTPS 접근, 비밀/권한 분리, 백업/복구, 운영 안내 | 최소 권한으로 운영하고 문제 발생 시 조회·복구 절차 수행 가능 |

1차 공개 범위는 로그인·권한 + 대시보드 + 회원 상세 + 차트 조회 + 대전/정산 조회 + 원장 + 감사 기록이다. 결제 메뉴는 메뉴 설계에 포함하되 실제 연동 전에는 미연동 상태를 명시한다. 다음으로 차트 배포와 제재/보상 기능을 붙이고 양 플랫폼 결제를 연결한다.

결제 구현에는 Unity 구매 UI/플랫폼 SDK 연결, 스토어 상품 등록, 서버 연동과 외부 통지 수신 주소가 함께 필요하다. 관리자 화면만 구현해서 결제가 가능해지는 것으로 완료 처리하지 않는다.

개발 일정은 단계 0에서 화면 수·팀 구성·기존 게임 결제 UI 상태·스토어 개발 계정 준비 상태를 확인한 뒤 산정한다. 이 기획 단계에서는 확정하지 않는다.

## 13. 구현 전에 확정할 업무 정책

Android·iOS 동시 지원은 사용자 답변으로 확정했다. 아래 항목은 아직 제안/미정이다.

1. 첫 판매 상품: Coin, Jem, 꾸미기 중 무엇을 판매하며 일회성 상품만 시작할지.
2. 유료/무료 재화의 소비 순서와 양 플랫폼 계정에서의 사용 범위.
3. 이미 사용한 재화의 환불·미회수 및 재구매/대전 제한 기준.
4. 운영 보상·차트 배포·분쟁 처리의 승인 역할과 금액 기준.
5. 초기 운영자 수, 문의 접수 수단, 상세 로그 보관 기간.
6. 개발/운영 서버와 Google Play/App Store 개발자 계정·상품 등록 준비 상태.

이 항목들과 무관하게 1단계 관리자 기반 및 조회 화면 설계는 진행할 수 있다.
