# 별도 서버 없이 뒤끝에서 정산하는 연결안

> 검토 결과: 이 문서의 새 데이터베이스 연결안은 보류한다. 뒤끝 담당자는 2026-02-24 [공식 커뮤니티 답변](https://community.thebackend.io/t/topic/11164)에서 데이터베이스의 펑션 이용을 지원하지 않으며 단기간 지원 예정도 없다고 안내했다. 현재 내려받은 SDK에서도 지원 경로를 확인하지 못했다. 이후 지원 변경 여부가 확인되기 전 이 설계로 운영 이전을 진행하지 않는다. 데이터베이스 활성화 완료는 펑션 연동 가능성을 의미하지 않는다.

2026-10-06 사용자는 뒤끝 외에 운영 서버가 없다고 확인했다. 새 외부 서버를 전제로 하지 않고 뒤끝 펑션과 뒤끝 데이터베이스 연결을 검토한다. 콘솔의 데이터베이스 소개도 펑션 서버 연동과 클라이언트 수정 제한을 용도로 안내한다. 실제 SDK의 서버 권한과 트랜잭션 경쟁 처리는 배포 전 확인해야 한다.

## 기존 게임 정보와 새 데이터베이스의 차이

기존 UserMain/MatchHistory/UserMatchHistory는 베이스의 게임 정보다. 새 데이터베이스는 독립된 저장소다. 두 저장소에 걸친 한 번의 원자적 트랜잭션이 제공된다고 가정할 수 없다. 기존 UserMain을 잔액 원본으로 유지하면서 새 데이터베이스에 중복 방지 원장만 저장하는 방식은 일부 성공·일부 실패 때 재지급 또는 미지급이 생길 수 있다.

따라서 이 경로를 채택하면 코인과 종목별 전적의 원본을 같은 새 데이터베이스에 두고 게임 정보의 UserMain은 프로필 용도로 쓰거나 갱신 가능한 표시 사본으로 사용해야 한다. 실제 기존 잔액의 이전은 별도 검토·검증 후 진행한다. 두 저장소의 Coin 값을 동시에 원본으로 취급하지 않는다.

## 준비할 서버 전용 테이블

| 테이블 | 기본 키 | 핵심 필드 | 보관 |
| --- | --- | --- | --- |
| MatchWallet | UserId | Coin, Ball_3_Win/Lose/Draw, Ball_4_Win/Lose/Draw, Version | 누적 유지 |
| MatchState | MatchId | UserA/B, Ball, HallId, EntryCoin, Phase, ReadyA/B, LastSeenA/B, ReportA/B, Version | 진행·복구 정책에 따라 유지 |
| MatchReceipt | MatchId | UserA/B, Ball, ResultA/B, EntryA/B, RewardA/B, Reason, SettledAt | 영구 중복 방지용 최소 원장 |
| MatchDetail | MatchId | 규칙, 시작/종료 시각, 점수, 닉네임, ExpiresAt | 정산 후 6개월 |

ClientAccess는 차단하고 펑션에서 참가자 인증 후 필요한 조회만 제공하는 방향이다. MatchId와 UserId는 기본 키로 고유성을 보장한다. 서버 SDK 접근이 확인되기 전 운영 테이블과 잔액을 이동하지 않는다.

## 정산 트랜잭션 설계

경기 시작은 MatchState 상태 전환과 양쪽 MatchWallet 차감을 같은 트랜잭션으로 처리한다. 경기 종료는 고유 MatchReceipt 삽입, 상태 확정, 양쪽 지갑과 전적 갱신, 상세 기록을 같은 트랜잭션으로 처리한다. 이미 있는 영수증의 삽입이 실패하면 전체 쓰기가 취소되어야 한다.

별도 경기에서 같은 지갑을 갱신하는 경쟁은 Version 조건 또는 DB의 원자적 Inc/Dec 및 잔액 조건으로 보호한다. 조건이 맞지 않아 0행을 수정했을 때 나머지 작업도 모두 실패하는지 반드시 확인한다. 작업 완료 후 TotalAffectedRows만 검사하는 것은 이미 커밋된 일부 변경을 취소하지 못하므로 대안이 아니다. 이 의미가 SDK에서 보장되지 않으면 조건부 쓰기/서버 트랜잭션의 다른 지원 경로를 확인해야 한다.

기존 Private UserMatchHistory를 정산 트랜잭션에 포함할 수 없다면 정산 원본에서 개인 기록 조회를 제공하고, 기존 테이블은 각 사용자의 비권위적 표시 사본으로만 사용한다. 상세 기록 사본의 실패는 원본 지급을 다시 실행시키지 않는다.

## 검증 순서

1. 데이터베이스 생성 완료와 서버 전용 접근 방법 확인.
2. 테스트 전용 데이터로 고유 키 충돌 시 전체 롤백, 잔액 부족 조건, 동시 호출, 두 사용자 갱신을 검증.
3. 기존 UserMain 실제 잔액·전적을 읽기 전용으로 비교하고 이전 계획 확정.
4. 게임의 잔액·전적 조회를 새 원본으로 전환하고 함수 호출 연결.
5. 실제 두 계정으로 정상 승리·무승부·기권·이탈·재시도 확인 후 적용.

테스트 단계에서 실제 사용자 코인이나 전적은 바꾸지 않는다. 현재 구현된 도메인 검사 28개는 2번의 실제 DB 검증을 대신하지 않는다.

## 실제 패키지 확인 결과

공식 npm 패키지 `com.backnd.database` 0.0.18을 작업 도구 캐시에 내려받아 소스를 확인했다. 프로젝트 패키지에는 설치하지 않았다. 제공된 Client/DatabaseExecutor는 UnityEngine, UnityWebRequest, Unity 루프를 사용하고 로그인 사용자 헤더로 초기화한다. 이 소스를 .NET 8 펑션의 서버 전용 SDK라고 간주해 그대로 참조할 수 없다. 공개 Client에는 별도 서버 관리자 인증 초기화가 확인되지 않았다.

콘솔에서 FREE 데이터베이스 활성화 완료를 확인했다. 서울 리전이며 테이블은 아직 0개다. 기존 게임 정보의 사용자 잔액과 전적은 이전하거나 변경하지 않았다. 운영 구현의 다음 선행 조건은 펑션에서 사용할 서버 API/SDK 및 서버 전용 인증 방법을 확인하는 것이다. Unity 클라이언트의 접근 권한을 넓히거나 내부 통신 헤더를 추측하여 서버 권한을 우회하지 않는다.

패키지 TransactionBuilder의 최대 작업 수 코드(100)와 현재 공식 문서(10)도 다르므로, 실서버 검증 전에는 보수적으로 10개 이내로 설계한다.
